Cloudflare Workers で自分のサイトを公開する計画書
―― GitHub Pages と同じ、独自ドメインを持たない方式

A Launch Plan for Domain-Free Static Hosting: Publishing a Personal Site on Cloudflare Workers, Modeled on GitHub Pages

独自ドメインを取らず、リポジトリへの push だけで公開する。いま使っている GitHub Pages のサイトと同じ型の運用を、 Cloudflare の Workers で実現するための工程と日程をまとめた。結論を先に書くと、この方式ではネームサーバーの切り替えは要らず、工程は大幅に少なくなる。ただし、いまの用途なら GitHub Pages のままで足りる可能性も高く、その比較を 1.2 に置いた。

【確認の範囲と限界】 2026 年 10 月 7 日に Cloudflare の公式ドキュメントで確認できた事項と、確認できていない事項を区別して書いた。確認できていないものは、本文中で「要確認」と明記している。公式ページの内容は、取得したページの要約で確認したもので、原文との逐語の照合はしていない。コマンドや設定値は、実作業の前に原典で照合してほしい。サイトの構成についての記述は、筆者が公開ページから取得した内容に基づく。 GitHub Pages の制限などは、 GitHub の公式ドキュメントの要約で確認した。

1. GitHub Pages の方式を Cloudflare に置き換える

いま使っているサイトは、 https://morihrkz.github.io/library/ という URL で公開されている。独自ドメインは持たず、 GitHub のアカウント名とリポジトリ名で URL が決まり、リポジトリへ push すれば公開される方式である。 Cloudflare の Workers にも、これと同じ型の運用がある。

1.1 URL と運用の対応関係

項目GitHub PagesCloudflare Workers
公開 URL の型アカウント名.github.io/リポジトリ名/Worker名.アカウントのサブドメイン.workers.dev [1]
URL の決まり方アカウント名とリポジトリ名Worker 名と、アカウントごとのサブドメイン。後者はダッシュボードで変えられるが、変えると配下のすべての Worker の URL が変わる [1]
独自ドメイン不要不要
更新の流れpush で公開Git に接続すると、 push のたびに自動でデプロイされる [3]
費用無料静的ファイルへの要求は無料で、回数の上限もない [2]
URL のパス部分リポジトリ名がパスになる(/library/)先頭にパスは付かない。同じ形にしたければ、公開ディレクトリの下に library フォルダを作り、その中にファイルを置く（要確認）

Worker 名は、 63 文字以内で、英数字とハイフンだけを使い、ハイフンで始めることも終えることもできない。 [1] この名前が URL の先頭になるので、たとえば Worker を library と名付ければ、 library.アカウントのサブドメイン.workers.dev になる。

1.2 GitHub Pages と Cloudflare Workers の長所と短所

先に、二つの疑問に答えておく。「 Cloudflare Workers は GitHub の利用が必須なのか」と、「必須なら GitHub Pages のほうが単純ではないか」である。

一つ目の答えは、必須ではないである。手元から npx wrangler deploy を実行すれば、 GitHub を介さずに公開できる。 [10] Git との接続は任意の機能で、対応する接続先は GitHub のほか、 GitLab と Cloudflare 自身のものがある。 [3] 逆に GitHub Pages は、 GitHub のリポジトリのファイルをそのまま公開する仕組みで、リポジトリが前提になる。 [19]

二つ目の答えは、いまの用途なら、そのとおりである。公開リポジトリのまま、静的な HTML を、いまの規模で公開し続けるだけなら、追加の作業が要らない GitHub Pages のほうが単純である。 Cloudflare Workers を選ぶ理由は、下に挙げる Cloudflare 側の長所が、実際に必要になったときに生まれる。

GitHub Pages長所短所
主な特徴
  • すでに使っており、新しいアカウントも、追加の設定も要らない
  • 公開元は、ブランチのルートか /docs フォルダを選ぶだけ。ビルドが必要なら GitHub Actions も使える [21]
  • ファイルを置くだけで公開され、 404.html も置くだけで効く [22]
  • 現に .html のリンクで構成したサイトが動いており、転送の差を気にしなくてよい
  • 依存先が GitHub だけで、増えない
  • 無料プランでは、公開リポジトリが前提になる。非公開のまま公開するには、有料プランが要る [20]
  • 公開サイトは 1 GB まで、帯域は月 100 GB （目安）、ビルドは 1 時間に 10 回（目安）、デプロイは 10 分で打ち切られる [18]
  • 事業のための、取引や SaaS を主な目的とするサイトは、用途として認められていない [18]
  • HTTP ヘッダーの指定や、サーバー側のリダイレクトができない（第三者の解説による。公式での確認はしていない。要確認）[23]
Cloudflare Workers長所短所
主な特徴
  • GitHub が要らない。手元から直接公開でき、 Git に接続するかどうかは選べる [10]
  • 静的ファイルへの要求は無料で、回数の上限もない [2]
  • _redirects と _headers で、リダイレクトとヘッダーを指定できる [11]
  • Git に接続すると、ブランチごとにプレビュー用の URL が作られる [3]
  • 後から、サイトにプログラムを足せる。機能の幅は Pages より広いと、 Cloudflare が説明している [6]
  • 手順が多い。 Cloudflare のアカウント、 Node.js 、 wrangler 、設定ファイル、 Git 接続が要る。 GitHub Pages は、設定画面で選ぶだけで済む
  • Git を使うなら、 GitHub と Cloudflare の二つに依存することになる
  • 無料プランのビルドは、月 3,000 分、同時 1 件までである [13]
  • /foo.html が既定で /foo へ転送されるなど、 GitHub Pages と挙動が違い、確認が要る [7]
  • プレビュー用などの URL も公開されるので、置くものに注意が要る [1]
  • 非公開のリポジトリを接続できるかが、読んだ資料からは分からない（要確認）

どちらを選ぶかは、次の条件で考えるとよい。

こういう場合は向いているのは
公開リポジトリのまま、静的な HTML を、いまの規模で公開し続けるGitHub Pages のまま。乗り換える理由が弱い
リポジトリを公開したくない、または GitHub を使わずに公開したいCloudflare Workers （非公開リポジトリの扱いは要確認）
HTTP ヘッダーやリダイレクトを、自分で制御したいCloudflare Workers
帯域やビルドの目安を、気にしたくないCloudflare Workers
将来、プログラムによる処理を足したい、または独自ドメインを Cloudflare に集約したいCloudflare Workers
取引や事業を主な目的とするサイトにするGitHub Pages は用途として認められていないので、 Cloudflare Workers 。ただし Cloudflare 側の利用条件は、確認できていない
どちらが合うか分からない二重に公開して試す。 GitHub Pages を止めずに済むので、損失はない

1.3 ネームサーバーの切り替えが要らなくなる理由

前の版では、独自ドメインを使う前提で、ネームサーバーを Cloudflare に切り替える工程を中心に組んでいた。その根拠は、 Workers では「ネームサーバーが Cloudflare に管理されていないドメイン」が使えず、 [4] カスタムドメインの追加にも有効な Cloudflare のゾーンが必要だ、という点にある。 [5] 比較表の「真価を発揮するには、ネームサーバーを Cloudflare 自体に切り替える構成が推奨される」という一文も、あくまで自分で取得した独自ドメインを載せる場合の話である。

workers.dev のホスト名は、 Cloudflare 自身が用意したものである。自分で取得したドメインではないので、利用者が DNS を設定する場面がなく、ネームサーバーを動かす必要もない（筆者の理解。公式の文言としては未確認）。 GitHub Pages で github.io のアドレスを使っているのと、同じ事情である。

なお、 Cloudflare 自身は新規プロジェクトに Workers を勧めている。 Pages の公式ドキュメントの冒頭には、 Workers は Pages のほとんどの用途に対応し、より広い機能を持つこと、新規プロジェクトは Workers で始めることが書かれている。 [6]

1.4 違いと注意点

  • URL は Cloudflare 側で決まる形になる。独自ドメインと違い、将来ほかの置き場へ移ると、 URL が変わる。読者や他のページからのリンクを維持したいなら、その時点で独自ドメインを取る意味が出てくる
  • アカウントのサブドメインを変えると、すべての Worker の URL が変わる。公開後は、むやみに変えない
  • 公開用の URL は一つとは限らない。 workers.dev の経路を止めても、版ごとの URL 、プレビュー用の URL 、デプロイごとの URL は止まらない。 [1] 公開したくないものは、そもそも公開ディレクトリに置かない
  • .html で終わるリンクの扱いが、 GitHub Pages と違う。既定の設定では、 /foo.html への要求は /foo へ 307 で転送される。 [7] いまのサイトは、相対リンクで .html のページをつないでいるので、転送を経由して表示されるはずだが、工程 5 で全ページを確かめる。ファイル名どおりに返したい場合は、設定で HTML の扱いを "none" にする方法がある

既存のリポジトリを流用する場合は、 GitHub Pages の公開を止めずに、同じファイルを Cloudflare にも公開できる。まず二重に公開して試し、うまく動いたあとで、どちらかに一本化するかを決めればよい。

2.2 順序を入れ替えてはいけない箇所

この順序なぜ入れ替えてはいけないか
公開してよいファイルを決める → デプロイする 公開ディレクトリに入っているファイルは、配信の対象になる。設定ファイルや下書きを公開したくなければ、別の場所に置くか、 .assetsignore で除外する [8]
ローカルで確認する → workers.dev へデプロイして確認する 不具合が、ファイルにあるのか、配信設定にあるのかを切り分けるため
Worker を一度デプロイして作る → Git に接続する Workers Builds は、既存の Worker に接続する形で案内されている。また、ダッシュボード上の Worker 名と設定ファイルの name が一致しないと、ビルドは失敗する [3]
Cloudflare 側の検証を終える → GitHub Pages 側を止めるかどうかを決める 止めると旧 URL が使えなくなり、旧 URL を知っている読者やリンクが切れる。新しい側で全ページを確かめてから決める

4. 各工程の作業内容

工程 0 〜 1 : 決定とアカウント

工程 0 では、まず、そもそも乗り換えるかどうかを、 1.2 の表で判断する。乗り換える場合は、次の三つを決めて文書に残す。一つ目は Worker 名である。これが URL の先頭になるので、あとから変えると URL が変わる。二つ目はリポジトリで、いまの library を流用するか、新規に作るかを決める。三つ目は公開ディレクトリの構成で、リポジトリの直下をそのまま公開するか、公開用のフォルダを分けるか、 URL に /library/ に相当するパスを付けるかを決める。

工程 1 の Cloudflare のアカウント作成と認証情報の入力は、必ずご自身で行う。 Claude Code が代行できない作業である。二要素認証も有効にする。 GitHub のアカウントは、すでにお持ちのものを使う。

工程 2 : 設定ファイルの作成とローカル確認

スクリプトを持たない静的サイトの、最小の設定は次のとおりである（公式の例による）。 name は Worker の名前、 compatibility_date には実作業の日付を入れ、 directory に公開するファイルを置く場所を指定する。 not_found_handling を "404-page" にすると、一致するファイルがない要求に、最も近い 404.html が 404 の状態で返る。 [9]

{
  "name": "library",
  "compatibility_date": "2026-10-07",
  "assets": {
    "directory": "./public/",
    "not_found_handling": "404-page"
  }
}

既存のリポジトリに、この設定ファイルを足す形が自然である。新規に雛形から作る場合は、公式の手順として、次のコマンドが案内されている。 Node.js が入っていることが前提になる。 [10]

npm create cloudflare@latest -- my-static-site
# 対話で Template に「Static site」を選び、「Deploy now」は「No」にする
cd my-static-site
npx wrangler dev        # ローカルで確認する

公開ディレクトリの中に、公開したくないファイルがある場合は、そのディレクトリの直下に .assetsignore を置く。書式は .gitignore と同じで、一致するファイルは、アップロードされない。 [8] リダイレクトとヘッダーは、同じディレクトリに _redirects と _headers を置いて指定できる。 _redirects の上限は、静的 2,000 件と動的 100 件の計 2,100 件である。 [11] 規模の上限は、 1 回の版あたり 20,000 ファイル（無料プラン）、 1 ファイル 25 MiB である。 [15] 75 本の記事なら、十分に収まる。

工程 3 : 初回デプロイと workers.dev での確認

初回の公開は、手元から次のコマンドを実行する。成功すると、 workers.dev の標準 URL でサイトが見られる。 Cloudflare アカウントへのログイン操作は、ご自身で行う。 [10]

npx wrangler deploy

アカウントのサブドメインをまだ決めていない場合は、初回のデプロイ中に設定を促される、と検索で確認した（公式の逐語での確認はしていない）。ここで決めた名前が、以後のすべての Worker の URL に入る。公開後に変えると URL が変わるので、落ち着いて決める。

工程 4 : Git への接続

ダッシュボードの Workers & Pages で該当の Worker を開き、 Settings > Builds > Connect から GitHub のリポジトリを選ぶ。デプロイのコマンドの既定は npx wrangler deploy 、監視するブランチの既定は main 、ビルドのコマンドは任意である。ビルド工程のない静的サイトなら、ビルドのコマンドは空でよい。 [3][12]

接続後は、 push するたびに自動でデプロイされ、本番以外のブランチには、プレビュー用の URL が作られる。 GitHub のアプリは、ビルドしたいリポジトリだけに権限を絞るよう、公式が勧めている。 [14] 無料プランのビルドは、月 3,000 分、同時 1 件、 1 回 20 分までである。 [13] 非公開のリポジトリを接続できるかは、読んだ資料からは読み取れなかったので、必要なら公式で確認する（要確認）。

工程 5 : 検証

  • ☐ トップページが表示され、文字化けがない
  • ☐ 索引から、全 75 本の記事へ移動でき、リンク切れがない
  • ☐ .html で終わるリンクが、転送を経由しても正しいページに着く
  • ☐ 存在しないパスで、用意した 404 ページが 404 の状態で返る
  • ☐ スマートフォンからのアクセスで、表示が崩れない
  • ☐ push すると自動でデプロイされ、変更が反映される

リンクの確認は、手作業だと漏れやすいので、状態コードを一括で調べるとよい。次は、記事の一覧を urls.txt に一行ずつ書いて確認する例である。

# Mac (zsh) / Linux
while read u; do curl -s -o /dev/null -L -w "%{http_code} $u\n" "$u"; done < urls.txt

# Windows PowerShell 7
Get-Content urls.txt | ForEach-Object { try { $r = Invoke-WebRequest $_ -MaximumRedirection 5; $r.StatusCode } catch { $_.Exception.Response.StatusCode.value__ }; $_ }

転送を経由する挙動が気になる場合や、 GitHub Pages とまったく同じ振る舞いにしたい場合は、設定の assets に "html_handling": "none" を足して試す。 "none" は、ファイルの完全一致だけを返す設定である。 [7] ただし、このとき / へのアクセスで index.html が返るかは確認できていないので、必ず手元で試す（要確認）。

工程 6 : 公開と運用への移行

公開日の前日に、検証リストを再実施する。告知は、検証が済んでからにする。 GitHub Pages と二重に公開している場合は、どちらを正とするかを決める。 GitHub Pages を止めると、旧 URL が使えなくなる。旧 URL を知っている読者やリンクが残るなら、しばらく併存させるのが安全である。

なお、 workers.dev の経路そのものを止める場合は、ダッシュボードの Settings > Domains & Routes で無効にするか、設定ファイルに "workers_dev": false を書く。ダッシュボードだけで止めて設定ファイルに書かないと、次回のデプロイで再び有効になる。 [1] ただし、独自ドメインを持たない今回の方式では、これを止めると、サイトにアクセスする手段がなくなる。止めてはならない。

5. 公開後の運用と、後から独自ドメインを足すとき

公開後の運用は、いまの GitHub Pages とほとんど変わらない。 HTML を更新して push すれば、公開される。次の点を、公開前に決めておくとよい。

  • アカウントの保護 : 二要素認証を有効にし、回復手段を安全な場所に保管する
  • サブドメインの扱い : アカウントのサブドメインを変えると、すべての Worker の URL が変わる。変えない前提で運用する
  • 更新手順 : 更新したら push する、という運用を文書にして残す
  • 撤退の経路 : 静的なファイルだけなので、 GitHub Pages に戻すのは容易である。リポジトリはそのまま残る
独自ドメインを後から足すとき
将来、独自ドメインを取りたくなったら、次の作業が増える。 Cloudflare にゾーンを追加し、レジストラでネームサーバーを Cloudflare のものに切り替え、 DNSSEC を設定している既存のドメインなら先に無効にし、有効化を確認してから、 Worker のカスタムドメインに追加する。 [16][17][5] Workers は、ネームサーバーが Cloudflare に管理されていないドメインをサポートしないので、 DNS を別の事業者に残す構成は選べない。 [4]
