EmDash 入門
――アカウントの作成から、最初の記事の公開まで

作成日 : 2026-10-24 ／ 出典の取得日 : 2026-10-24 ／ 本文は取得日の時点の情報に基づく

この記事は、頭から順に読みながら、手を動かして進める手順書である。 Cloudflare のアカウントを作るところから始め、 CMS 「 EmDash 」を自分のパソコンで動かし、同じサイトを Cloudflare に載せて、インターネットに記事を公開するところまでを扱う。各章の終わりに「ここまでの確認」を置いた。確認の条件を満たしてから、次の章に進んでほしい。

0. 作るもののあらましと、用意するもの

EmDash は、 Cloudflare が公開する MIT ライセンスの CMS （コンテンツ管理システム。 Web サイトの文章や画像を、画面から書いて管理する仕組み）である。 Astro （ Web サイトを作るための枠組み）の上に作られ、 TypeScript で書かれている [1] 。この記事では、この CMS を Cloudflare の次の三つの部品の上で動かす。

部品役割
Workersサイトの本体と管理画面を動かす実行環境。自分でサーバーを用意し、管理する必要がない [5]
D1記事などの文章を入れるデータベース [5]
R2画像などのファイルを入れる保存領域 [5]

完成すると、サイトは https://（サイトの名前）.（自分の名前）.workers.dev という URL （ブラウザのアドレス欄に入れる文字列）で公開され、世界のどこからでも見られるようになる。独自のドメイン（ example.com のような、自分専用の名前）は取らない。

0.1 用意するもの

  • Windows または Mac のパソコン。ターミナル（文字で命令を打ち込む画面）を使う。 Windows では PowerShell 、 Mac では「ターミナル」を使う。
  • メールを受け取れるメールアドレス（ Cloudflare の登録で使う）。
  • ブラウザ。パスキー（パスワードの代わりになる認証）が使えるもの。
  • 所要時間の目安は、順調なら 2 〜 3 時間である。
EmDash は 2026 年 9 月に版 1.0 が公開されたばかりである [2] 。ネットにある古い解説は、 1.0 より前の版の手順で書かれていることがある。たとえば emdash dev などのコマンドは、 1.0 で削除された [3] 。この記事に書いたコマンドと、手元の画面が食い違ったら、公式ドキュメント [4][5] を優先してほしい。

1. Cloudflare のアカウントを作る

この章の作業は、すべてブラウザで行う。

  1. ブラウザで https://dash.cloudflare.com/sign-up を開く [12] 。
  2. メールアドレスとパスワードを入れ、「 Create Account 」を選ぶ [12] 。パスワードは、他のサイトと使い回さない長いものにする。
  3. 確認のメールが届く。メールの中のリンクを開き、メールアドレスの確認を済ませる [12] 。
  4. ダッシュボード（ Cloudflare の管理画面）にログインできることを確かめる。
  5. 二要素認証（パスワードに加えて、もう一つの手段で本人を確かめる仕組み）を有効にする。ダッシュボード右上のプロフィールから、認証（ Authentication ）の設定を開き、認証アプリなどを登録する。メニューの文言は変わりうるので、画面の表示に従う。登録したら、回復用のコードを安全な場所に保管する。
契約するプランは、無料のもので足りる。ただし、後の章で R2 を使い始める際に、支払い方法の登録を求める画面が出ることがある。この点は、公式の料金ページでは確認できなかった。 R2 の無料枠は、保存 10 GB 、書き込み系の操作が月 100 万回、読み出し系の操作が月 1,000 万回である [13] 。 D1 の無料枠は、保存 5 GB 、 1 日に読む行が 500 万行、書く行が 10 万行である [14] 。求められた場合は、無料枠の範囲で使い続けるつもりかを自分で決めてから、登録する。
ここまでの確認
ダッシュボードにログインでき、二要素認証が有効になっている。

2. 道具をそろえる

EmDash の雛形（作り始めの土台となるファイル一式）を作って動かすには、 Node.js （サーバー側で JavaScript を動かす実行環境）が要る。 EmDash の公式のはじめ方は、 Node.js 22.23.4 以上を求めている [4] 。

  1. ターミナルを開く。 Windows では、スタートメニューで「 PowerShell 」を探して開く。 Mac では、「ターミナル」を開く。
  2. 次を打って、 Node.js の版を調べる。 
    node --version
    「 v22.23.4 」以上の数字が出れば、次へ進む。「コマンドが見つからない」と出るか、版が古い場合は、 https://nodejs.org/ から LTS （長期サポート版）の最新を入れ、ターミナルを開き直して、もう一度調べる。 LTS の最新が 22.23.4 以上であることは、入れたあとの node --version で確かめる。
  3. パッケージマネージャー（部品の取り込みを管理する道具）の pnpm を入れる。この記事は pnpm で統一する。 
    npm install -g pnpm
pnpm --version
    版の数字が出れば成功である。 Mac で権限のエラーが出るときは、先頭に sudo を付けて打つ。
ここまでの確認
node --version が 22.23.4 以上、 pnpm --version が数字を返す。

3. 雛形を作る

EmDash には、公式の雛形が用意されている。雛形は、ブログ、マーケティング用のページ、作品集、汎用の Starter の四種類があり、それぞれに Cloudflare 向け（ D1 と R2 を使う）と Node.js 向け（ SQLite とパソコン内の保存領域を使う）がある [6] 。この記事では、汎用の Starter の Cloudflare 向けを使う。

  1. 雛形を置きたい場所へ移動する。ここでは書類フォルダを例にする。 
    cd ~/Documents
  2. 雛形の作成を始める。 
    pnpm create emdash@latest
  3. 質問に答える。公式のはじめ方では、次のように答えている [4] 。ただし、この記事は Cloudflare に載せるので、 2 番目の質問だけ変える。
    質問答え
    Project namemy-emdash-site （好きな名前でよい。英数字とハイフンだけにする）
    Where will you deploy?Cloudflare Workers を選ぶ。選択肢の文言は、画面の表示に従う（公式のはじめ方は Node.js の場合だけを説明しており、この選択肢の文言は確認できなかった）
    Which template?Starter
    Which package manager?pnpm
    Install dependencies?Yes
  4. 終わったら、できたフォルダに入る。 
    cd my-emdash-site

依存部品の取り込みに失敗したときも、ファイルは残る。作成ツールが表示する再実行のコマンドを打つ [4] 。

雛形の質問に Cloudflare の選択肢が見当たらないときは、次の方法で同じものを得る。雛形の置き場 [6] から starter-cloudflare のフォルダを手元にコピーし、そのフォルダで pnpm install を実行する。
ここまでの確認
my-emdash-site のフォルダができ、その中に wrangler.jsonc と astro.config.mjs がある。

4. 自分のパソコンで動かし、記事を一本公開する

いきなり Cloudflare に載せず、まず手元で動かす。うまくいかないとき、原因が EmDash の側にあるのか、 Cloudflare の設定にあるのかを切り分けられるからである。

4.1 起動する

  1. 次を打つ。 
    pnpm dev
  2. ターミナルに、手元のサイトを開くための URL が出る。通常は http://localhost:4321/ である [4] 。このターミナルは、閉じずに開いたままにする。

4.2 最初の設定を済ませる

  1. ブラウザで http://localhost:4321/_emdash/admin/ を開く。新しいサイトでは、設定の案内（セットアップウィザード）に自動で移る [4] 。
  2. 「 Site Title 」にサイトの名前を入れる。「 Tagline 」（ひとこと説明）は空でもよい。「 Include sample content 」（見本の内容を含める）は選んだままにして、「 Continue 」を選ぶ [4] 。
  3. 「 Your Email 」にメールアドレスを入れる。名前は任意である。「 Continue 」を選ぶ [4] 。
  4. ブラウザがパスキーの登録を求めるので、画面の案内に従って登録する。登録後、「 Open the dashboard 」を選ぶ [4] 。

4.3 記事を編集して公開する

  1. 管理画面の「 Posts 」を開き、「 Welcome 」の記事を開く [4] 。
  2. 題を Hello from EmDash に変えて「 Save 」を選ぶ [4] 。
  3. 「 Publish changes 」を選ぶ [4] 。
  4. 新しいタブで http://localhost:4321/ を開く。トップページに「 Hello from EmDash 」が並んでいれば成功である [4] 。
この章の雛形は、手元で動かすときの保存先（データベースと画像）を自動で用意する。 Cloudflare 向けの雛形を手元で動かしたときの保存先の細部は、公式の記述では確認できなかった。ここで作った記事は、 Cloudflare に公開したサイトには引き継がれない。公開後に、あらためて作る。
ここまでの確認
手元のサイトのトップページに、題を変えた記事が表示されている。

5. 公開の前に、構成ファイルを読む

手元で動いたので、 Cloudflare に載せる前に、雛形に入っている設定の意味を知っておく。ここは読むだけで、書き換えない。 Ctrl + C でいったん pnpm dev を止めてから、エディターで my-emdash-site のフォルダを開く。

5.1 wrangler.jsonc ― Cloudflare への指示書

Wrangler は、 Cloudflare の設定と公開のためのコマンドである。 wrangler.jsonc は、何をどの名前で用意するかを書いた指示書である。公式ガイドが示す例は次のとおりである [5] 。雛形の中身は、これと近い形のはずだが、日付や名前は雛形のほうが正しい。

{
  "name": "my-emdash-site",
  "main": "./src/worker.ts",
  "compatibility_date": "2026-02-24",
  "compatibility_flags": ["nodejs_compat"],
  "d1_databases": [{ "binding": "DB", "database_name": "my-emdash-site" }],
  "r2_buckets": [{ "binding": "MEDIA", "bucket_name": "my-emdash-media" }],
  "worker_loaders": [{ "binding": "LOADER" }],
  "triggers": { "crons": ["* * * * *"] }
}
項目意味
nameWorker の名前。公開後の URL の先頭の部分になる。 63 文字以内で、英数字とハイフンだけを使い、ハイフンで始めることも終えることもできない [7]
main入口になるファイル。 src/worker.ts
d1_databases記事を入れるデータベース。 DB という名前（バインディング。 Worker から資源を呼ぶための名前）で呼び出す
r2_buckets画像を入れる保存領域。 MEDIA という名前で呼び出す
worker_loaders隔離されたプラグインを動かす仕組み（ LOADER ）。プラグインを使わないなら省ける [5]
triggers.crons定期的に動く処理。予約投稿の公開などを動かす [5]
DB 、 MEDIA 、 LOADER の名前は、 EmDash が期待する名前と一致させる必要がある [5] 。書き換えない。

D1 のデータベースと R2 の保存領域は、 Cloudflare の側にまだ無くても、初回の公開で Wrangler が作る [5] 。後の公開で同じ資源につなぎ直すため、ここに書かれた名前は変えない [5] 。

5.2 astro.config.mjs と src/worker.ts

astro.config.mjs は、サイト全体の設定である。公式ガイドの例では、サーバーでの描画を指定し、 Cloudflare 用の部品と React （管理画面が React で作られているため必要）を有効にする。そのうえで EmDash に、データベースとして d1({ binding: "DB" }) 、保存先として r2({ binding: "MEDIA" }) を渡す。隔離プラグインを使わないなら、 sandboxRunner: sandbox() の一行は不要である [5] 。

src/worker.ts は、定期処理の入口 createScheduledHandler() を接続し、プラグインの橋渡し PluginBridge を書き出す小さなファイルである。隔離プラグインを使わないうちも、 PluginBridge の書き出しは残す [5] 。

ここまでの確認
三つのファイルを開いて、上の表の項目がどこに書かれているかを指させる。

6. 暗号鍵を控える

手元の雛形を作ったとき、作成ツールは EMDASH_ENCRYPTION_KEY という暗号鍵を作り、 .env というファイルに書いた [4] 。この鍵は、プラグインの秘密の設定を暗号化するためのもので、失うと、暗号化した設定を読み出せなくなる [4][5] 。公式のはじめ方は、公開の前に控えを取ることを求めている [4] 。

  1. .env を開き、 EMDASH_ENCRYPTION_KEY= の右側の文字列を、パスワード管理アプリなどの安全な場所に保存する。
  2. .env を、 Git のリポジトリには入れない [4] 。メールやチャットにも貼らない。
ここまでの確認
鍵の控えが、このフォルダの外にある。

7. Cloudflare に公開する

7.1 ログインする

pnpm wrangler login

ブラウザが開き、 Cloudflare への接続を許可するかを尋ねられる。 1 章で作ったアカウントでログインし、許可する。ターミナルに戻ると、ログインの成功が表示される [5] 。

7.2 公開する

雛形の README は、公開のコマンドを pnpm deploy と案内している [6] 。

pnpm deploy

このコマンドが「見つからない」と表示されたときは、公式ガイドの二段の手順で同じことをする [5] 。

pnpm build
pnpm wrangler deploy

初回の公開では、次のことが起きる。

  • D1 のデータベースと R2 の保存領域が、 Cloudflare の側に作られる [5][6] 。 R2 で支払い方法の登録を求められたら、 1 章の注意を読み返す。
  • アカウントのサブドメイン（ URL のうち「自分の名前」の部分）を、まだ決めていない場合は、決めるよう促されることがある。この動作は、検索で確認したもので、公式の文面は確認していない。ここで決めた名前は、このアカウントのすべての Worker の URL に入る。あとから変えると、それらの URL がすべて変わる [7] 。落ち着いて決める。
  • 成功すると、ターミナルに、公開先の URL が https://（Worker の名前）.（サブドメイン）.workers.dev の形で表示される [5][7] 。

7.3 すぐに管理画面の最初の設定をする

これは急ぐ作業である。公開したサイトでは、最初の設定を終えた人が管理者になる。しかも、この設定では、そのときアクセスしている URL が記録される [5] 。公開が成功したら、サイトの URL を他人に知らせる前に、自分で設定を終える。
  1. 表示された URL の末尾に /_emdash/admin/ を足して、ブラウザで開く。たとえば https://my-emdash-site.自分の名前.workers.dev/_emdash/admin/ である。入口がローカルと同じであるかは、公式の記述では確認していない。開けなければ、トップページから管理画面への案内を探す。
  2. 4.2 と同じ手順で、サイト名、メールアドレス、パスキーを設定する。パスキーは、手元で作ったものとは別に、あらためて登録する。

最初の要求の際、 EmDash はデータベースの基本の準備を自動で行う [5] 。最初の表示だけは、待たされることがある。

ここまでの確認
公開先の URL でトップページが表示され、その管理画面にログインできている。

8. 公開したサイトに、最初の記事を書く

  1. 公開したサイトの管理画面で「 Posts 」を開く。 7.3 で見本の内容を含めた場合は、「 Welcome 」の記事がある。
  2. 4.3 と同じ手順で、題を変え、「 Save 」と「 Publish changes 」を選ぶ。または、新しい記事を作って公開する。
  3. 7.2 で表示された URL を、別のブラウザ、またはスマートフォンで開く。自分の記事が見えれば、インターネットへの公開は完了である。

8.1 画像で R2 を確かめる

管理画面から画像を一枚アップロードし、記事に入れて公開する。公開したサイトの記事で画像が表示されれば、 R2 が働いている。

8.2 サイトを直して、公開し直す

記事の内容は、管理画面で直せば、すぐに反映される。サイトの見た目や設定をファイル側で変えたときは、手元で動作を確かめてから、もう一度公開する。

pnpm deploy

手元で確かめるときは、 pnpm dev を使う。

ここまでの確認
別の端末のブラウザから、自分で書いた記事と画像が見える。

9. 公開後の点検

最後に、次の項目を一つずつ確かめる。公式ガイドは、公開の点検として、公開ページの取得、管理画面へのログイン、メディアのアップロードと取得、定期処理の動作の確認を挙げている [5] 。

  • ☐ 公開したサイトのトップページが開き、文字化けがない
  • ☐ 管理画面にログインでき、記事を作成して公開できる
  • ☐ 画像をアップロードして、記事に表示できる
  • ☐ 存在しないパスを開くと、エラーの画面が返る
  • ☐ スマートフォンで見て、表示が崩れない
  • ☐ 暗号鍵の控えが、リポジトリの外の安全な場所にある
  • ☐ 次のコマンドで、定期処理が動いている 
    pnpm emdash doctor
pnpm wrangler tail
    wrangler tail は、公開した Worker の動きを、ターミナルに流し続ける。止めるには Ctrl + C を押す。定期処理の設定を変えた直後は、動き出すまでに最長で 15 分かかることがある [5] 。

これで、「アカウントを作る」から「記事を公開する」までの工程は終わりである。

10. うまくいかないとき

症状確かめること
公開したサイトを開くと 503 が返る大きなデータの移行が未適用の可能性がある。 pnpm emdash migrate を実行する [5]
「 D1 binding not found 」wrangler.jsonc の DB と、 astro.config.mjs の d1({ binding: "DB" }) の名前が一致しているか [5]
「 R2 binding not found 」MEDIA と r2({ binding: "MEDIA" }) の名前が一致しているか [5]
移行のエラーpnpm wrangler tail を動かしたまま、同じ操作を再現して、出力を読む [5]
pnpm dev が起動しないnode --version が 22.23.4 以上か。 pnpm install をやり直す
画像が表示されない、または原寸のまま出る画像の変換には IMAGES のバインディングが要る。ない場合は、原寸で配信されるか、失敗する [5] 。無料枠は月 5,000 件の変換までで、超えるとエラー 9422 になる [5]
メールによるログインで「 Email is not configured 」本番でのメールの送信には、 send_email のバインディングと、確認済みの送信元ドメインが要る [5] 。パスキーでのログインなら不要

11. この先の選択肢

ここから先は、手順書の範囲を超える発展である。必要になったときに読む。

11.1 秘密の値の保存

プラグインに秘密の設定を持たせるときは、 pnpm wrangler secret put EMDASH_ENCRYPTION_KEY のように、秘密の値を Cloudflare に保存する。値は wrangler.jsonc には書かない [5] 。保存すべき値が、 6 章で控えた鍵と同じものかは、公式ガイドの記述から確認できなかった。プラグインを使う前に、原典で確かめる。

11.2 Git につなぎ、 push で自動公開する

手順は、ダッシュボードの Workers & Pages で該当の Worker を開き、 Settings > Builds から GitHub のリポジトリを接続する、というものである [8] 。 Worker を一度公開してから接続する順序になる。ダッシュボード上の Worker 名と、設定ファイルの name が一致しないと、ビルドは失敗する [8] 。デプロイのコマンドの既定は npx wrangler deploy 、監視するブランチの既定は main である [9] 。 EmDash は公開の前に pnpm build が要るので、ビルドのコマンドの欄に入れる必要があるはずだが、確認していない。無料プランのビルドには、月間の時間などの上限がある。

11.3 独自のドメインを足す

公式ガイドは、 workers.dev の URL でサイトが応答することを確かめてから、 wrangler.jsonc に経路を足して、公開し直すよう述べる [5] 。 Workers のカスタムドメインには、有効な Cloudflare のゾーン（ Cloudflare に管理を預けたドメイン）が要る [10] 。ドメインの取得の手順は、この記事では扱わない。

workers.dev の URL でのアクセスを止める設定は、独自ドメインを足すまで使わない。止めると、サイトにアクセスする手段がなくなる [7] 。

11.4 AI エージェントからの操作

EmDash は、 CLI と、 AI エージェントが接続して操作する窓口（ MCP サーバー）を、標準で備える [1] 。接続先は /_emdash/api/mcp である。認証には、 OAuth 2.1 、個人アクセストークン、デバイス認可の三つの方式があり、操作できる範囲はスコープ（許可の単位）で絞れる [11] 。サイト全体の移転に使うツールは、管理者だけが使える [11] 。
