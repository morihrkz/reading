EmDash を Cloudflare で動かして学ぶ ― 構成の理解から公開・運用までの道のり

作成日 : 2026-10-24 ／ 出典の取得日 : 2026-10-24 ／ 本文は取得日の時点の情報に基づく

この記事は、 Cloudflare の CMS 「 EmDash 」を、 Cloudflare の環境（ Workers 、 D1 、 R2 ）の上で実際に動かしながら学ぶための手引きである。 EmDash の概要、 Cloudflare 上の構成、学習の道のり、公開と運用の計画の順に述べる。結論は、調べた事実の範囲で導く。調べていない事項と、報道の食い違いは、末尾の「限界」で述べる。

1. 問いと方法

主題の問いは、 Cloudflare の環境を使って EmDash を動かし、操作し、学ぶには、何をどの順にすればよいのか、である。学ぶ場所は Cloudflare に絞る。他の CMS との比較や、既存のサイトからの移行は扱わない。

本文の事実は三つに区分して示す。 確立した事実 は一次情報（公式リポジトリ・公式ドキュメント）で確認したものを指す。 未確定 は二次情報（報道・解説記事）にとどまり、検証が足りないものを指す。 投機 は将来の予測を指す。

2. EmDash の概要

確立した事実 EmDash は、 Cloudflare が公開する MIT ライセンスの CMS （コンテンツ管理システム。 Web サイトの文章や画像を管理する仕組み）である。公式リポジトリは、 EmDash を Astro （ Web サイトを作るための、 TypeScript 製の枠組み）に基づく TypeScript （ JavaScript に型の宣言を加えた言語）の CMS と説明している [1] 。

未確定 版 1.0 は、 2026 年 9 月 28 日頃に公開されたと報じられている。報道は、ベータを脱した無料の CMS と紹介している [2] 。プレビューは 2026 年 4 月頃に公開されたと報じられている [8] 。公開からの期間が短い。

確立した事実 公式の移行ガイドは、 0.x の版（ 1.0 より前の版）から 1.0 への更新で「 Removed 」として扱う項目を四つ挙げている [3] 。その四つは、関数 cloudflareCache()、 emdash/ui からの Comments と CommentForm の書き出し（ emdash/ui/comments からは引き続き使える）、 CLI のコマンド emdash dev と emdash auth secret 、設定の experimental.registry である。 1.0 以後の破壊的変更（既存の利用方法が動かなくなる変更）は、メジャー版（版番号の先頭の数字が変わる版）でのみ行うとリリース情報に書かれている [4] 。古い資料の手順は、この削除の影響を受けていないか確かめてから使う。

確立した事実 実行環境は、 Cloudflare の Workers （ Cloudflare が提供する、サーバーの管理を要しない実行環境）と D1 （データベース）、 R2 （ファイル保存領域）、または SQLite （小型のデータベース）を使う、 Node.js （サーバー上で JavaScript を動かす実行環境）のサーバーである [1] 。プラグインは Dynamic Worker Loaders （隔離された実行環境を作る Cloudflare の仕組み）と呼ばれる環境で動き、使う能力を宣言するマニフェスト（プラグインが使う能力を宣言する書類）を持つ [1] 。

確立した事実 CLI （ターミナルから操作する道具）と、 MCP サーバー（ AI エージェントが接続して操作する窓口）が標準で組み込まれている [1] 。 MCP の接続先（エンドポイント。通信の届け先）は /_emdash/api/mcp である。認証は Bearer トークン（合言葉に当たる文字列）による。方式は、 OAuth 2.1 （外部のサービスで許可を得る仕組み）、個人アクセストークン、デバイス認可（ターミナルなど、画面の限られた道具で認証する方式）の三つである。操作できる範囲は、スコープ（許可の単位）で絞る [5] 。サイト全体の移転に使うツールは、管理者 (Admin) だけが使える [5] 。

未確定 プラグインの隔離の強度は、実行環境によって異なる可能性がある。報道は、 Cloudflare 上の隔離に有料プランを要すると書く一方、 Node.js 上でも workerd （ Cloudflare の実行環境の基盤）で隔離できると書く。前者は 1.0 より前のレビューの記述である。信頼モードでは宣言が文書上の意味にとどまり、強制されるのはサンドボックスモードのみとする二次情報もある。この二つは食い違っており、本記事は確定しない [6] 。なお、 Cloudflare への公開手順の公式ガイドは、特定のプランの名前を挙げていない [11] 。

3. Cloudflare 上の EmDash の構成

確立した事実 この章は、公式の Cloudflare 向け公開ガイド [11] の内容を、取得した要約に基づいて整理したものである。コードと設定値は、実作業の前に原典で照合してほしい。

3.1 部品と役割

部品役割設定上の名前
Workersサイト本体と管理画面を動かす実行環境。入口は src/worker.tsmain 、 name
D1記事などのデータを入れるデータベースバインディング DB
R2画像などのメディアのファイルを入れる保存領域バインディング MEDIA
Worker Loader隔離されたプラグインを動かす仕組み。マーケットプレイス、レジストリ、サンドボックスのプラグインを使わないなら省けるバインディング LOADER
Cron Trigger予約公開、プラグインの定期処理、バックアップ、保守を駆動するtriggers.crons

バインディング（Worker から D1 や R2 などの資源を呼ぶための名前）の DB 、 MEDIA 、 LOADER は、 EmDash のアダプターが期待する名前と一致させる必要がある [11] 。 D1 のデータベースと R2 のバケットは、初回のデプロイ時に存在しなければ Wrangler （ Cloudflare の設定・公開用コマンド）が作る [11] 。

3.2 設定ファイルの例

公式ガイドが示す wrangler.jsonc は次のとおりである。 compatibility_date は公式の例の日付なので、実作業では作業日の日付にする。

{
  "name": "my-emdash-site",
  "main": "./src/worker.ts",
  "compatibility_date": "2026-02-24",
  "compatibility_flags": ["nodejs_compat"],
  "d1_databases": [{ "binding": "DB", "database_name": "my-emdash-site" }],
  "r2_buckets": [{ "binding": "MEDIA", "bucket_name": "my-emdash-media" }],
  "worker_loaders": [{ "binding": "LOADER" }],
  "triggers": { "crons": ["* * * * *"] }
}

Astro の設定（ astro.config.mjs ）では、サーバー描画を指定し、 Cloudflare のアダプターと React を有効にする。 React が要るのは、管理画面が React のアプリだからである。そのうえで EmDash に、データベースとして d1({ binding: "DB" }) 、保存先として r2({ binding: "MEDIA" }) を渡す。隔離プラグインを使うなら sandboxRunner: sandbox() も渡し、使わないなら省く [11] 。

src/worker.ts は、定期処理の入口 createScheduledHandler() を接続し、プラグインの橋渡しの PluginBridge を書き出す小さなファイルである [11] 。

3.3 公開の手順と、公式が挙げる注意

pnpm wrangler login      # 初回のみ。ブラウザで認証する
pnpm build
pnpm wrangler deploy
  • 移行処理 : 既定の auto では、最初の要求で基本の移行処理が走る。大きな内容の移行は emdash migrate で行う必要があり、それまで Worker は 503 を返す [11]
  • 確認 : 定期処理は pnpm emdash doctor と pnpm wrangler tail で確かめる [11]
  • 秘密の値 : pnpm wrangler secret put <名前> で保存し、 wrangler.jsonc には書かない。 EMDASH_ENCRYPTION_KEY は、秘密として宣言されたプラグインの設定を暗号化する鍵で、プラグインの秘密を保存する前に設定し、 D1 のバックアップとは別に控える [11]
  • 画像の変換 : Images の無料枠は、月 5,000 件の変換までである。超えると新しい変換はエラー 9422 になる [11]
  • メール : 本番では send_email のバインディングと、確認済みの送信元ドメインが要る。メールの設定がないと、メールによるログイン（マジックリンク）は「 Email is not configured 」と表示される [11]
  • 独自ドメイン : workers.dev の URL が応答することを確かめてから、 wrangler.jsonc に経路を足して再公開する [11]
ローカルで動かす入門は、別の公式ページにある。必要な Node.js は 22.23.4 以上である [9] 。 npm create emdash@latest で雛形を作り、 npm run dev で起動すると http://localhost:4321/ で動く。管理画面は /_emdash/admin/ で、初期設定ではサイト名とメールアドレスを入れ、パスキー（パスワードの代わりになる認証方式）を登録する。雛形の質問「 Where will you deploy? 」の選択肢のうち、確認できたのは Node.js だけである。 Cloudflare を選べるかは、取得した要約では分からなかった（要確認）。この雛形は SQLite とローカルの保存領域を使うので、 D1 と R2 を使う構成とは設定が異なる。 .env に生成される EMDASH_ENCRYPTION_KEY は、公開前に控えを取り、リポジトリには入れない [9] 。

5. 2026 年 10 月から始める道のり

この章は、 4 章の表の 1 行目と 2 行目に当てはまる読者に向けた道のりである。起点は 2026 年 10 月、期間は 6 か月（ 2027 年 3 月まで）、学習時間は週 5 時間を仮定する。これらは筆者の仮定である。各段階の長さと所要時間は、筆者の見積もりであり、合計は約 107 時間となる。
  1. 基礎（ 10 月下旬〜 11 月中旬、約 15 時間と見積もる）。 目標は、 EmDash の構成（ Astro の上の CMS で、 Workers 、 D1 、 R2 に載る）を説明できることである。ターミナルの操作、 Node.js 、 TypeScript の読み方、 Cloudflare の用語（ Worker 、バインディング）を学ぶ。終わりに、 3 章の表を自分の言葉で書き直した構成図と説明文を一つずつ作る。
  2. ローカルでの構築（ 11 月中旬〜 12 月中旬、約 20 時間と見積もる）。 目標は、雛形から作った検証用のサイトを手元で動かし、管理画面で記事を一本公開することである。 Node.js の版の要件は 22.23.4 以上である [9] 。古い二次情報には 22.12 以上や 22.16 以上とするものもあるが、公式の記述を優先する。終わりに、起動した画面と、公開した記事の記録を残す。
  3. Cloudflare への公開（ 12 月中旬〜 1 月下旬、約 25 時間と見積もる）。 目標は、同じサイトを Workers 、 D1 、 R2 の構成に載せ、 workers.dev の URL で動かすことである。手順は 6 章に置く。終わりに、公開した検証サイトと、 wrangler.jsonc の各項目の意味を説明した文書を示す。
  4. 拡張（ 2 月、約 25 時間と見積もる）。 プラグインか MCP のどちらか一方を選ぶ。 MCP は、個人アクセストークンか、スコープを絞った OAuth で認証する [5] 。プラグインを選ぶ場合は、 Worker Loader を有効にした構成で試す。終わりに、動作した手順を記録する。
  5. 運用（ 3 月、約 22 時間と見積もる）。 版の更新、バックアップと復元、秘密の値と権限の設計を手順にする。終わりに、一度の更新と一度の復元を記録する。

6. Cloudflare で EmDash を動かす計画

この章は、 5 章の 3 段階目「 Cloudflare への公開」を実行するための計画書である。 EmDash の設定と手順は、 2026 年 10 月 24 日に公式ドキュメントの要約で確認した [9][11] 。 Cloudflare 一般の仕様（ workers.dev 、 Git 接続など）は、 2026 年 10 月 7 日に確認した公式ドキュメントに基づく。確認できていない事項は、本文中で「要確認」と明記している。公式ページの内容は、取得したページの要約で確認したもので、原文との逐語の照合はしていない。コマンドや設定値は、実作業の前に原典で照合してほしい。

6.2 順序を入れ替えてはいけない箇所

この順序なぜ入れ替えてはいけないか
ローカルで動かす → Cloudflare に公開する不具合が、 EmDash のコードにあるのか、 Cloudflare の設定にあるのかを切り分けるため
暗号鍵を控える → 公開する公式の入門が公開前の控えを求めている [9] 。鍵を失うと、暗号化したプラグインの設定を読めなくなる
秘密の値を設定する → プラグインの秘密を保存するEMDASH_ENCRYPTION_KEY が先に要る [11]
Worker を一度公開して作る → Git に接続するWorkers Builds は、既存の Worker に接続する形で案内されている。また、ダッシュボード上の Worker 名と設定ファイルの name が一致しないと、ビルドは失敗する [14]
workers.dev で動作を確かめる → 独自ドメインを足す公式ガイドが、この順を求めている [11]

6.4 各工程の作業内容

工程 0 〜 1 : 決定とアカウント

工程 0 では、 Worker 名を決める。これが URL の先頭になるので、あとから変えると URL が変わる。 D1 と R2 の名前は、 3 章の例のように分かりやすく付ける。隔離プラグインを使うかどうかで、 LOADER と sandboxRunner の要否が決まる。プランの要否は報道の間で食い違うので [6] 、使う場合は公開の時点で動作を確かめる。

工程 1 の Cloudflare のアカウント作成と認証情報の入力は、必ずご自身で行う。 Claude Code が代行できない作業である。二要素認証も有効にする。

工程 2 : ローカルでの構築

3 章の枠内に示した入門の手順で、雛形を作って起動する [9] 。管理画面で、サイト名とメールアドレスを入れ、パスキーを登録し、記事「 Welcome 」の題を変えて公開する。ここで EmDash の画面と、記事が保存される流れをつかむ。 .env の EMDASH_ENCRYPTION_KEY は、この時点で控えを取る。

工程 3 : Cloudflare 向けの構成

3 章の設定ファイルの例を参考に、次を行う。 Astro の設定を Cloudflare のアダプターと D1 、 R2 に切り替える。 wrangler.jsonc と src/worker.ts を作る。 compatibility_date を作業日にする。 SQLite とローカル保存領域から D1 と R2 に切り替わると、工程 2 で作った記事は引き継がれないため、記事は公開後に作り直す（引き継ぎ方法は未確認。要確認）。終わりに pnpm build を実行して、成功を確かめる。

工程 4 : 初回の公開と初期設定

工程 3 のあと、 pnpm wrangler login でログインし、 pnpm wrangler deploy を実行する。 Cloudflare アカウントへのログイン操作は、ご自身で行う。成功すると、 workers.dev の標準 URL でサイトが見られる [11][12] 。アカウントのサブドメインをまだ決めていない場合は、初回の公開中に設定を促される、と検索で確認した（公式の逐語での確認はしていない）。ここで決めた名前が、以後のすべての Worker の URL に入るので、落ち着いて決める。

最初の要求で、基本の移行処理と、雛形の初期データの投入が走る [11] 。管理画面の入口が、ローカルと同じ /_emdash/admin/ であるかは確認していない（要確認）。入れたら、初期設定を済ませて、記事を一本公開する。 503 が返る場合は、 emdash migrate が必要な状態かを疑う [11] 。

工程 5 : 秘密の値と Git への接続

秘密の値は pnpm wrangler secret put EMDASH_ENCRYPTION_KEY で保存する。値は工程 2 で控えた鍵を使うのか、新しく作るのかを、公式ガイドで確かめる（要確認）。

Git への接続は、ダッシュボードの Workers & Pages で該当の Worker を開き、 Settings > Builds > Connect から GitHub のリポジトリを選ぶ。デプロイのコマンドの既定は npx wrangler deploy 、監視するブランチの既定は main 、ビルドのコマンドは任意である。 EmDash は公開前に pnpm build が要るので、ビルドのコマンドにそれを入れる必要があるはずだが、確認していない（要確認）。 [14][15] 接続後は、 push するたびに自動で公開され、本番以外のブランチには、プレビュー用の URL が作られる。 GitHub のアプリは、ビルドしたいリポジトリだけに権限を絞るよう、公式が勧めている [17] 。無料プランのビルドは、月 3,000 分、同時 1 件、 1 回 20 分までである [16] 。

工程 6 : 検証と運用への移行

  • ☐ 標準 URL でトップページが表示され、文字化けがない
  • ☐ 管理画面にログインでき、記事を作成して公開できる
  • ☐ 画像をアップロードして、記事に表示できる（ R2 の確認）
  • ☐ pnpm emdash doctor と pnpm wrangler tail で、定期処理が動いている
  • ☐ 存在しないパスで、エラーの画面が適切に返る
  • ☐ スマートフォンからのアクセスで、表示が崩れない
  • ☐ push すると自動で公開され、変更が反映される
  • ☐ 暗号鍵の控えが、リポジトリの外の安全な場所にある

公開日の前日に、検証リストを再実施する。 workers.dev の経路そのものを止める場合は、ダッシュボードの Settings > Domains & Routes で無効にするか、設定ファイルに "workers_dev": false を書く。ダッシュボードだけで止めて設定ファイルに書かないと、次回の公開で再び有効になる。 [12] 独自ドメインを持たない今回の方式では、これを止めると、サイトにアクセスする手段がなくなる。止めてはならない。また、版ごとの URL やプレビュー用の URL は止まらないので [12] 、公開したくない内容は入れない。

6.5 Claude Code との分担

この計画の作業は、 Claude Code と一緒に進めることを想定している。 Claude Code は、ターミナルで文字の命令を実行し、その出力を読んで次の手を決める道具である。ボタンの位置を目で探してクリックする作業は、得意な使い方ではない。本計画の wrangler や emdash のコマンドは、入力も結果も文字で済むので、任せやすい。繰り返しも容易で、公開した Worker を作り直す手間も小さい。ただし、何でも任せてよいわけではない。

工程 0名前と構成の決定各案の影響の整理、決定事項の文書化

  • EmDash 自身の MCP サーバーは、別の話である。 5 章の拡張の段階で、 Claude Code から公開した EmDash を操作する場合に使う [5] 。権限のスコープを絞り、管理者だけが使えるサイト全体の移転のツールには触れさせない [5]

Cloudflare は、 Claude Code 向けの公式のセットアップ手順も公開している。 2026 年 10 月 22 日時点の検索結果の要約では、 Cloudflare 向けの Skills と、 API ・ドキュメント・ビルド・可観測性などの MCP サーバーを Claude Code に登録する構成で、 API の MCP サーバーは 2,500 以上のエンドポイントを少ないトークン量で扱える、と説明されている [20] 。この項は検索結果の要約で確認したもので、公式ページの本文は精読していない。本計画の範囲では、 wrangler のコマンドだけで足りる可能性が高く、導入が必要かは未確認である（要確認）。

6.6 公開後の運用と、後から独自ドメインを足すとき

  • アカウントの保護 : 二要素認証を有効にし、回復手段を安全な場所に保管する
  • 鍵の保管 : EMDASH_ENCRYPTION_KEY は、 D1 のバックアップとは別に控える [11]
  • サブドメインの扱い : アカウントのサブドメインを変えると、すべての Worker の URL が変わる。変えない前提で運用する
  • 版の更新 : 更新の前に、移行ガイドの削除項目を確かめる [3]
  • 更新手順 : 更新したら push する、という運用を文書にして残す
独自ドメインを後から足すとき
公式ガイドは、 workers.dev の URL が応答することを確かめてから、 wrangler.jsonc に経路を足して再公開する、と述べる [11] 。 Cloudflare 一般の条件として、 Workers のカスタムドメインには有効な Cloudflare のゾーンが要り [18] 、ネームサーバーが Cloudflare に管理されていないドメインはサポートされない [19] 。ドメインの取得とネームサーバーの切り替えの手順は、この記事では扱わない。

本章は公式ドキュメントの確認に基づく計画書であり、実際の作業結果ではない。「要確認」と記した事項、および出典に「未精読」と付した事項は、実作業の前に原典で確かめること。料金プラン、画面の文言、各社の仕様は変更されうる。
