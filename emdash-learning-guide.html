2. EmDash の概要

確立した事実 EmDash は、 Cloudflare が公開する MIT ライセンスの CMS （コンテンツ管理システム。 Web サイトの文章や画像を管理する仕組み）である。公式リポジトリは、 EmDash を Astro （ Web サイトを作るための、 TypeScript 製の枠組み）に基づく TypeScript （ JavaScript に型の宣言を加えた言語）の CMS と説明し、 WordPress の「精神的後継」という語を説明文に使っている [1] 。この呼称は提供元の枠組みであり、本記事は事実の評価としては用いない。

未確定 版 1.0 は、 2026 年 9 月 28 日頃に公開されたと報じられている。報道は、ベータを脱した無料の CMS と紹介している [2] 。

確立した事実 公式の移行ガイドは、 0.x の版（ 1.0 より前の版）から 1.0 への移行で「 Removed 」として扱う項目を四つ挙げている [3] 。 その四つは、関数 cloudflareCache()、 emdash/ui からの Comments と CommentForm の書き出し（ emdash/ui/comments からは引き続き使える）、 CLI のコマンド emdash dev と emdash auth secret 、設定の experimental.registry である。 1.0 以後の破壊的変更（既存の利用方法が動かなくなる変更）は、メジャー版（版番号の先頭の数字が変わる版）でのみ行うとリリース情報に書かれている [4] 。

確立した事実 実行環境は、 Cloudflare の Workers （ Cloudflare が提供する、サーバーの管理を要しない実行環境）と D1 （データベース）、 R2 （ファイル保存領域）、または SQLite （小型のデータベース）を使う、 Node.js （サーバー上で JavaScript を動かす実行環境）のサーバーである [1] 。プラグインは Dynamic Worker Loaders （隔離された実行環境を作る Cloudflare の仕組み）と呼ばれる環境で動き、使う能力を宣言するマニフェスト（プラグインが使う能力を宣言する書類）を持つ [1] 。

確立した事実 CLI （ターミナルから操作する道具）と、 MCP サーバー（ AI エージェントが接続して操作する窓口）が標準で組み込まれている [1] 。 MCP の接続先（エンドポイント。通信の届け先）は /_emdash/api/mcp である。認証は Bearer トークン（合言葉に当たる文字列）による。方式は、 OAuth 2.1 （外部のサービスで許可を得る仕組み）、個人アクセストークン、デバイス認可（ターミナルなど、画面の限られた道具で認証する方式）の三つである。操作できる範囲は、スコープ（許可の単位）で絞る [5] 。サイト全体の移転に使うツールは、管理者 (Admin) だけが使える [5] 。

未確定 プラグインの隔離の強度は、実行環境によって異なる可能性がある。報道は、 Cloudflare 上の隔離に有料プランを要すると書く一方、 Node.js 上でも workerd （ Cloudflare の実行環境の基盤）で隔離できると書く。前者は 1.0 より前のレビューの記述である。信頼モードでは宣言が文書上の意味にとどまり、強制されるのはサンドボックスモードのみとする二次情報もある。この二つは食い違っており、本記事は確定しない [6] 。

6. 公開の基盤を決める ― Cloudflare Workers で静的サイトを公開する計画

この章は、 5 章の 2 段階目「構築」で検証用のサイトを公開するときの、公開の基盤の一つとして Cloudflare Workers を使う場合の計画書である。元は独立した計画書で、この記事に統合した。扱うのは、独自ドメインを持たず、 GitHub Pages と同じ型で静的な HTML のサイトを公開する方式であり、 EmDash を動かす手順ではない。内容の確認は 2026 年 10 月 7 日に行い、 2 〜 5 章より取得日が古い。確認できていない事項は、本文中で「要確認」と明記している。公式ページの内容は、取得したページの要約で確認したもので、原文との逐語の照合はしていない。コマンドや設定値は、実作業の前に原典で照合してほしい。サイトの構成についての記述は、筆者が公開ページから取得した内容に基づく。 GitHub Pages の制限などは、 GitHub の公式ドキュメントの要約で確認した。

独自ドメインを取らず、リポジトリへの push だけで公開する。いま使っている GitHub Pages のサイトと同じ型の運用を、 Cloudflare の Workers で実現するための工程と日程をまとめた。結論を先に書くと、この方式ではネームサーバーの切り替えは要らず、工程は大幅に少なくなる。ただし、いまの用途なら GitHub Pages のままで足りる可能性も高く、その比較を 6.1.2 に置いた。

6.1 GitHub Pages の方式を Cloudflare に置き換える

いま使っているサイトは、 https://morihrkz.github.io/library/ という URL で公開されている。独自ドメインは持たず、 GitHub のアカウント名とリポジトリ名で URL が決まり、リポジトリへ push すれば公開される方式である。 Cloudflare の Workers にも、これと同じ型の運用がある。

6.1.2 GitHub Pages と Cloudflare Workers の長所と短所

先に、二つの疑問に答えておく。「 Cloudflare Workers は GitHub の利用が必須なのか」と、「必須なら GitHub Pages のほうが単純ではないか」である。

一つ目の答えは、必須ではないである。手元から npx wrangler deploy を実行すれば、 GitHub を介さずに公開できる。 [29] Git との接続は任意の機能で、対応する接続先は GitHub のほか、 GitLab と Cloudflare 自身のものがある。 [22] 逆に GitHub Pages は、 GitHub のリポジトリのファイルをそのまま公開する仕組みで、リポジトリが前提になる。 [38]

二つ目の答えは、いまの用途なら、そのとおりである。公開リポジトリのまま、静的な HTML を、いまの規模で公開し続けるだけなら、追加の作業が要らない GitHub Pages のほうが単純である。 Cloudflare Workers を選ぶ理由は、下に挙げる Cloudflare 側の長所が、実際に必要になったときに生まれる。

GitHub Pages長所短所

  • 公開元は、ブランチのルートか /docs フォルダを選ぶだけ。ビルドが必要なら GitHub Actions も使える [40]
  • ファイルを置くだけで公開され、 404.html も置くだけで効く [41]
  • 現に .html のリンクで構成したサイトが動いており、転送の差を気にしなくてよい
  • 依存先が GitHub だけで、増えない

  • 公開サイトは 1 GB まで、帯域は月 100 GB （目安）、ビルドは 1 時間に 10 回（目安）、デプロイは 10 分で打ち切られる [37]
  • 事業のための、取引や SaaS を主な目的とするサイトは、用途として認められていない [37]
  • HTTP ヘッダーの指定や、サーバー側のリダイレクトができない（第三者の解説による。公式での確認はしていない。要確認）[42]

  • 静的ファイルへの要求は無料で、回数の上限もない [21]
  • _redirects と _headers で、リダイレクトとヘッダーを指定できる [30]
  • Git に接続すると、ブランチごとにプレビュー用の URL が作られる [22]
  • 後から、サイトにプログラムを足せる。機能の幅は Pages より広いと、 Cloudflare が説明している [25]
  • 手順が多い。 Cloudflare のアカウント、 Node.js 、 wrangler 、設定ファイル、 Git 接続が要る。 GitHub Pages は、設定画面で選ぶだけで済む
  • Git を使うなら、 GitHub と Cloudflare の二つに依存することになる
  • 無料プランのビルドは、月 3,000 分、同時 1 件までである [32]
  • /foo.html が既定で /foo へ転送されるなど、 GitHub Pages と挙動が違い、確認が要る [26]
  • プレビュー用などの URL も公開されるので、置くものに注意が要る [20]
  • 非公開のリポジトリを接続できるかが、読んだ資料からは分からない（要確認）

6.1.3 ネームサーバーの切り替えが要らなくなる理由

この計画の初期案では、独自ドメインを使う前提で、ネームサーバーを Cloudflare に切り替える工程を中心に組んでいた。その根拠は、 Workers では「ネームサーバーが Cloudflare に管理されていないドメイン」が使えず、 [23] カスタムドメインの追加にも有効な Cloudflare のゾーンが必要だ、という点にある。 [24] 比較表の「真価を発揮するには、ネームサーバーを Cloudflare 自体に切り替える構成が推奨される」という一文も、あくまで自分で取得した独自ドメインを載せる場合の話である。

workers.dev のホスト名は、 Cloudflare 自身が用意したものである。自分で取得したドメインではないので、利用者が DNS を設定する場面がなく、ネームサーバーを動かす必要もない（筆者の理解。公式の文言としては未確認）。 GitHub Pages で github.io のアドレスを使っているのと、同じ事情である。

なお、 Cloudflare 自身は新規プロジェクトに Workers を勧めている。 Pages の公式ドキュメントの冒頭には、 Workers は Pages のほとんどの用途に対応し、より広い機能を持つこと、新規プロジェクトは Workers で始めることが書かれている。 [25]

6.1.4 違いと注意点

  • URL は Cloudflare 側で決まる形になる。独自ドメインと違い、将来ほかの置き場へ移ると、 URL が変わる。読者や他のページからのリンクを維持したいなら、その時点で独自ドメインを取る意味が出てくる
  • アカウントのサブドメインを変えると、すべての Worker の URL が変わる。公開後は、むやみに変えない
  • 公開用の URL は一つとは限らない。 workers.dev の経路を止めても、版ごとの URL 、プレビュー用の URL 、デプロイごとの URL は止まらない。 [20] 公開したくないものは、そもそも公開ディレクトリに置かない
  • .html で終わるリンクの扱いが、 GitHub Pages と違う。既定の設定では、 /foo.html への要求は /foo へ 307 で転送される。 [26] いまのサイトは、相対リンクで .html のページをつないでいるので、転送を経由して表示されるはずだが、工程 5 で全ページを確かめる。ファイル名どおりに返したい場合は、設定で HTML の扱いを "none" にする方法がある

6.4 各工程の作業内容

工程 0 〜 1 : 決定とアカウント

工程 0 では、まず、そもそも乗り換えるかどうかを、 6.1.2 の表で判断する。乗り換える場合は、次の三つを決めて文書に残す。一つ目は Worker 名である。これが URL の先頭になるので、あとから変えると URL が変わる。二つ目はリポジトリで、いまの library を流用するか、新規に作るかを決める。三つ目は公開ディレクトリの構成で、リポジトリの直下をそのまま公開するか、公開用のフォルダを分けるか、 URL に /library/ に相当するパスを付けるかを決める。

工程 1 の Cloudflare のアカウント作成と認証情報の入力は、必ずご自身で行う。 Claude Code が代行できない作業である。二要素認証も有効にする。 GitHub のアカウントは、すでにお持ちのものを使う。

工程 2 : 設定ファイルの作成とローカル確認

スクリプトを持たない静的サイトの、最小の設定は次のとおりである（公式の例による）。 name は Worker の名前、 compatibility_date には実作業の日付を入れ、 directory に公開するファイルを置く場所を指定する。 not_found_handling を "404-page" にすると、一致するファイルがない要求に、最も近い 404.html が 404 の状態で返る。 [28]

{
  "name": "library",
  "compatibility_date": "2026-10-07",
  "assets": {
    "directory": "./public/",
    "not_found_handling": "404-page"
  }
}

既存のリポジトリに、この設定ファイルを足す形が自然である。新規に雛形から作る場合は、公式の手順として、次のコマンドが案内されている。 Node.js が入っていることが前提になる。 [29]

npm create cloudflare@latest -- my-static-site
# 対話で Template に「Static site」を選び、「Deploy now」は「No」にする
cd my-static-site
npx wrangler dev        # ローカルで確認する

公開ディレクトリの中に、公開したくないファイルがある場合は、そのディレクトリの直下に .assetsignore を置く。書式は .gitignore と同じで、一致するファイルは、アップロードされない。 [27] リダイレクトとヘッダーは、同じディレクトリに _redirects と _headers を置いて指定できる。 _redirects の上限は、静的 2,000 件と動的 100 件の計 2,100 件である。 [30] 規模の上限は、 1 回の版あたり 20,000 ファイル（無料プラン）、 1 ファイル 25 MiB である。 [34] 75 本の記事なら、十分に収まる。

工程 3 : 初回デプロイと workers.dev での確認

初回の公開は、手元から次のコマンドを実行する。成功すると、 workers.dev の標準 URL でサイトが見られる。 Cloudflare アカウントへのログイン操作は、ご自身で行う。 [29]

npx wrangler deploy

アカウントのサブドメインをまだ決めていない場合は、初回のデプロイ中に設定を促される、と検索で確認した（公式の逐語での確認はしていない）。ここで決めた名前が、以後のすべての Worker の URL に入る。公開後に変えると URL が変わるので、落ち着いて決める。

工程 4 : Git への接続

ダッシュボードの Workers & Pages で該当の Worker を開き、 Settings > Builds > Connect から GitHub のリポジトリを選ぶ。デプロイのコマンドの既定は npx wrangler deploy 、監視するブランチの既定は main 、ビルドのコマンドは任意である。ビルド工程のない静的サイトなら、ビルドのコマンドは空でよい。 [22][31]

接続後は、 push するたびに自動でデプロイされ、本番以外のブランチには、プレビュー用の URL が作られる。 GitHub のアプリは、ビルドしたいリポジトリだけに権限を絞るよう、公式が勧めている。 [33] 無料プランのビルドは、月 3,000 分、同時 1 件、 1 回 20 分までである。 [32] 非公開のリポジトリを接続できるかは、読んだ資料からは読み取れなかったので、必要なら公式で確認する（要確認）。

工程 5 : 検証

  • ☐ トップページが表示され、文字化けがない
  • ☐ 索引から、全 75 本の記事へ移動でき、リンク切れがない
  • ☐ .html で終わるリンクが、転送を経由しても正しいページに着く
  • ☐ 存在しないパスで、用意した 404 ページが 404 の状態で返る
  • ☐ スマートフォンからのアクセスで、表示が崩れない
  • ☐ push すると自動でデプロイされ、変更が反映される

リンクの確認は、手作業だと漏れやすいので、状態コードを一括で調べるとよい。次は、記事の一覧を urls.txt に一行ずつ書いて確認する例である。

# Mac (zsh) / Linux
while read u; do curl -s -o /dev/null -L -w "%{http_code} $u\n" "$u"; done < urls.txt

# Windows PowerShell 7
Get-Content urls.txt | ForEach-Object { try { $r = Invoke-WebRequest $_ -MaximumRedirection 5; $r.StatusCode } catch { $_.Exception.Response.StatusCode.value__ }; $_ }

転送を経由する挙動が気になる場合や、 GitHub Pages とまったく同じ振る舞いにしたい場合は、設定の assets に "html_handling": "none" を足して試す。 "none" は、ファイルの完全一致だけを返す設定である。 [26] ただし、このとき / へのアクセスで index.html が返るかは確認できていないので、必ず手元で試す（要確認）。

工程 6 : 公開と運用への移行

公開日の前日に、検証リストを再実施する。告知は、検証が済んでからにする。 GitHub Pages と二重に公開している場合は、どちらを正とするかを決める。 GitHub Pages を止めると、旧 URL が使えなくなる。旧 URL を知っている読者やリンクが残るなら、しばらく併存させるのが安全である。

なお、 workers.dev の経路そのものを止める場合は、ダッシュボードの Settings > Domains & Routes で無効にするか、設定ファイルに "workers_dev": false を書く。ダッシュボードだけで止めて設定ファイルに書かないと、次回のデプロイで再び有効になる。 [20] ただし、独自ドメインを持たない今回の方式では、これを止めると、サイトにアクセスする手段がなくなる。止めてはならない。

6.5 Claude Code との分担

この計画の作業は、 Claude Code と一緒に進めることを想定している。ただし、何でも任せてよいわけではない。この節では、任せられる理由と、人が持つべき範囲、任せるときの注意をまとめる。 Claude Code に任せる考え方は、 Cloudflare への移行を Claude Code と進めた人の記事に拠る。 [43] その記事は WordPress の会社サイトの移行を扱ったもので、独自ドメインを使う点が本計画と異なる。そのため、取り込んだのは考え方だけである。

6.5.1 なぜコマンドと API なら任せられるのか

記事の筆者は、 Cloudflare に移した最も大きな理由として、「コマンドと公開 API で全機能が触れるので、 Claude Code がそのまま作業できる」ことを挙げている。 [43] 本計画で使う npx wrangler deploy も、このコマンドの一つである。 Claude Code は、ターミナルで文字の命令を実行し、その出力を読んで次の手を決める道具である。ボタンの位置を目で探してクリックする作業は、得意な使い方ではない。操作がコマンドと API で閉じていると、次の三点で任せやすくなる。

  • 入力が文字で済む : 命令を書けば実行でき、画面の見た目に左右されない
  • 結果が文字で返る : 成功か失敗か、現在の状態がどうかを、出力から読み取って判断できる
  • 繰り返しと取り消しが容易 : 同じ命令を何度でも実行できる。本計画でも、静的ファイルだけの構成なので、 GitHub Pages に戻すのは容易である（6.6 を参照）

「全機能」という言い方は、筆者の実感であり、 Cloudflare のすべての機能を検証した主張ではない。本計画で必要な範囲に限っても、どこまでコマンドで済むかは、次の 6.5.2 で工程ごとに見る。

6.5.3 任せるときの注意

  • 渡す権限を絞る。 Claude Code にコマンドや API を使わせるには、認証情報（トークン）を渡す必要がある。渡す権限の範囲は、この作業に必要なものに絞る。記事にはこの点の記述がないので、筆者の一般的な理解として書く [43]
  • 操作できることと、検証を任せられることは別である。記事でも、切り替えのあとに見つかった欠け（フッター、解析タグ、スマートフォンの表示）は、人と AI が画面を見て確かめて見つけている。 [43] 本計画でも、工程 5 の目視確認と合否の判断は、人が持つ
  • 旧状態の記録は、人が設計する。切り替えの前に、旧 URL の一覧など、戻すときに必要な記録を残す。本計画では GitHub Pages を止めずに二重公開するので、戻る先が残る
  • 対象外の領域がある。本計画は独自ドメインを持たないので、レジストラの管理画面などは登場しない。もし後から独自ドメインを足すなら（6.6 を参照）、 Cloudflare の外にあるレジストラでの操作は、この分担の対象外になる
  • 記事は宣伝を兼ねている。記事の末尾は、 AI エージェント開発サービスの告知で終わっている。実体験に基づく評価として読めるが、宣伝を兼ねた文脈でもある [43]

6.5.4 Cloudflare 公式の Claude Code 向けセットアップ

記事とは別に、 Cloudflare は Claude Code 向けの公式のセットアップ手順を公開している。 2026 年 10 月 22 日時点の検索結果の要約では、 Cloudflare 向けの Skills と、 API ・ドキュメント・ビルド・可観測性などの MCP サーバーを Claude Code に登録する構成で、 API の MCP サーバーは 2,500 以上のエンドポイントを少ないトークン量で扱える、と説明されている。 [44]

この項は検索結果の要約で確認したもので、公式ページの本文は精読していない。本計画の範囲（静的ファイルの公開）では、 wrangler のコマンドだけで足りる可能性が高く、 MCP サーバーが必要かは未確認である（要確認）。導入するときは、公式ページの最新の手順を確かめること。

6.6 公開後の運用と、後から独自ドメインを足すとき

公開後の運用は、いまの GitHub Pages とほとんど変わらない。 HTML を更新して push すれば、公開される。次の点を、公開前に決めておくとよい。

  • アカウントの保護 : 二要素認証を有効にし、回復手段を安全な場所に保管する
  • サブドメインの扱い : アカウントのサブドメインを変えると、すべての Worker の URL が変わる。変えない前提で運用する
  • 更新手順 : 更新したら push する、という運用を文書にして残す
  • 撤退の経路 : 静的なファイルだけなので、 GitHub Pages に戻すのは容易である。リポジトリはそのまま残る
独自ドメインを後から足すとき
将来、独自ドメインを取りたくなったら、次の作業が増える。 Cloudflare にゾーンを追加し、レジストラでネームサーバーを Cloudflare のものに切り替え、 DNSSEC を設定している既存のドメインなら先に無効にし、有効化を確認してから、 Worker のカスタムドメインに追加する。 [35][36][24] Workers は、ネームサーバーが Cloudflare に管理されていないドメインをサポートしないので、 DNS を別の事業者に残す構成は選べない。 [23]

本章は 2026 年 10 月 7 日時点の公式ドキュメントの確認に基づく計画書であり、実際の作業結果ではない。「要確認」と記した事項、および出典に「未精読」と付した事項は、実作業の前に原典で確かめること。料金プラン、画面の文言、各社の仕様は変更されうる。
