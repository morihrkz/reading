Adabas とは何のための道具だったのか : メインフレームの大量取引を支えたデータベース

作成日 : 2026-10-21 ／ 種別 : 調査結果のまとめ ／ 調査方法 : Web 検索と、公開されている公式文書・記事の確認 ／ 前作 : Software AG とは何だったのか

結論 : Adabas は、 IBM などのメインフレームで、多数の端末から同時に届く大量の取引を、少ない計算資源で速く、止めずに処理するためのデータベースである。 1971 年に Software AG が発表した。リレーショナル（表）型ではなく「転置リスト」型で、検索の鍵となる項目ごとに索引を持つ。主に開発言語 Natural と組み合わせて使われ、銀行・保険・行政などの基幹業務の裏側にあった。

用途の具体的な顧客名は、今回確認できた資料では多くは出てこなかった。行政の例（カリフォルニア州技術局）と、移行を請け負う事業者の事例が主である。性能や費用削減の数字は、メーカーや移行事業者の自己申告が大半なので、そう明記した。

1要点

  • 名前は「 adaptable database system （適応できるデータベース）」の略で、 1971 年に非リレーショナルのデータベースとして出た。最初の版は IBM メインフレームの DOS/360 、 OS/MFT 、 OS/MVT で動いた。
  • 狙いは、大量のデータと大量の同時利用がある基幹業務を、少ない資源で処理すること。公式文書は、同種の製品の 10% から 50% の資源（ディスク、 CPU 、経過時間）で済むと述べる（メーカーの主張）。
  • データ構造は、項目 (field) 、レコード、ファイル、データベースの階層で、ファイルは表、レコードは行、項目は列にあたる。
  • 関係（親子など）は、実行時に表を結合して作るのではなく、構造として保持する前提の設計である。そのぶん、 CPU の消費が抑えられると説明される。
  • 7 日 24 時間の運用を想定し、稼働したまま読み書き・バックアップができる。障害後は自動で回復する。
  • 2016 年に Software AG は、 Adabas と Natural を 2050 年以降も支援すると発表した。いまも Linux 、 Unix 、 Windows 向けを含めて販売されている。

2何のために使われたか

2.1 想定された仕事

公式文書は、数テラバイトのデータと数千台の端末をもつ大規模なオンライン業務を支えるものとして説明している。 Wikipedia は、大量データの処理と、取引の多いオンライン処理に使われると書く。つまり、集計や分析のために作られた製品ではなく、日々の受付・更新・照会を絶え間なく繰り返す業務のためのものである。

用途の側面内容確度
大量のオンライン取引多数の端末からの同時の照会・更新を、レコード単位の保持（ロック）と取引の確定／取消で整合させる公式文書にもとづく
停止しない運用稼働中のままファイルの読み書き、バックアップ、復元、性能分析ができる公式文書にもとづく
資源の節約項目の圧縮と、必要な項目だけを読む呼び出しで、ディスクと CPU を抑えるメーカーの主張
行政の基幹業務カリフォルニア州技術局が、州の機関向けにメインフレーム上の共通サービスとして提供している（毎秒 100 万コマンド超という性能を掲げる）運用側の説明（性能値はメーカー由来とみられる）
給与・金融・保険などの業務移行事業者の事例に、給与システムや州政府のシステム、資産運用会社が登場する事業者の事例（自己申告）

2.2 なぜ「速く、安い」と言われたか

理由は主に三つ述べられている。第一に、データを圧縮して持つこと。第二に、検索の鍵ごとに用意した索引（転置リスト）で、該当レコードの位置をすぐ引けること。第三に、関係を実行時の結合に頼らず、構造として持つことである。公式文書は、多くのファイルで元データの 50% から 60% の容量で済む（索引などの約 25% を足した後でも）と述べる。

3仕組み

3.1 三つの領域

Adabas は、データ本体と、データを探すための仕組みを分けて持つ。

領域役割
Data Storage （データ記憶域）圧縮されたレコードを置く。ブロックには 1% から 90% （既定 10% ）の余白があり、レコードが伸びても別の場所へ動かさずに済む
Associator （アソシエータ）データを探すための構造を置く。項目定義表 (FDT) 、転置リスト、アドレス変換表などがここにある
Work （作業域）自動復旧に使う保護情報、検索の途中結果と最終結果（ ISN のリスト）、二相コミットの情報を置く

3.2 ISN とアドレス変換表

各レコードには ISN （内部通番）が付く。新しいレコードには、既存の最大値に 1 を足した番号が付くのが基本である。 ISN と物理的な位置の対応は「アドレス変換表」が持つので、レコードを別の場所へ動かしても、更新するのはこの表だけで済み、索引は変わらない。

3.3 転置リスト

検索の鍵になる項目（ディスクリプタ）ごとに、索引（転置リスト）を持つ。値ごとに「その値」「該当レコード数」「該当する ISN の並び」を記録する。レコードの順に値を並べる通常の索引と逆に、値を起点にレコードを引くので「転置」と呼ばれる。複数の項目を組み合わせた鍵（スーパーディスクリプタ、 2 から 20 項目）や、音の近さで引く鍵（フォネティック）も作れる。

3.4 繰り返しの持ち方

一つのレコードに同種の値を複数持つ「多値項目 (MU) 」と、項目の組を繰り返す「周期グループ (PE) 」がある。 MU は既定で 1 レコードあたり最大 191 回、設定により約 65,534 回まで持てる。 PE は繰り返しの順序を保つ点が MU と異なる。表を正規化して分けるかわりに、一つのレコードに畳み込む設計である。

4どう使われたか

4.1 アクセスの方法

プログラムは、直接の呼び出し（コマンド）で Adabas を使う。検索、読み出し、追加・更新・削除、取引の確定と取消などのコマンドがあり、必要な項目だけを取り出せる。実際には、多くの業務は開発言語 Natural の READ 、 FIND 、 HISTOGRAM などの文で書かれ、裏で Adabas が呼ばれる。バックエンドに Adabas を使う古い業務アプリケーションの多くが Natural で作られているのは、このためである。

4.2 同時利用と障害への備え

  • 更新するレコードは「保持」状態にされ、他の利用者は待たされる（待たずにエラーを受け取る指定もできる）。
  • 取引は、保持から確定 (ET) または取消 (BT) までを単位とする。複数のデータベースにまたがる取引は、二相コミットで調整する。
  • デッドロックのおそれは検出され、後から来た利用者にエラーが返る。
  • 障害後は自動で再開・取消が行われ、論理的に完結した取引だけが残る。ログとして、コマンドの記録、更新前後の記録（保護ログ）、復旧用の記録がある。

5リレーショナル型との違い

観点Adabas一般のリレーショナル型
基本の形ファイル・レコード・項目。転置リスト型表・行・列。 SQL で操作
SQL本体は持たない。 SQL ゲートウェイ経由 (2004 年に買収した CONNX の技術。 ODBC 、 JDBC 、 OLE DB)標準の操作言語
参照整合性本体では強制しない。親子の整合はアプリケーション側で保つ外部キー制約で強制できる
繰り返しデータMU と PE で一つのレコードに畳み込む別の表に分けて結合する
得意なこと決まった検索と更新を、大量に、速く自由な問い合わせと、表の組み合わせ

同じ転置リスト型の主要製品として、 Model 204 (Computer Corporation of America) と Datacom/DB (ADR) が挙げられている。 2015 年の IBM の白書は、 Adabas のような関係型以前のデータベースを、もはや主流ではないと評した。

7その後と、いまの位置

  • 動作環境の拡大 : 現在は BS2000 、 z/VSE 、 z/OS 、 Unix 、 Linux 、 Windows で動く。
  • 長期の支援 : 2016 年に、 2050 年以降まで支援すると表明した。
  • 移行の動き : 使用料と保守費、そして Natural の技術者の減少を理由に、他の基盤へ移す動きがある。移行事業者は、年間 50 万ドルから 150 万ドル超の使用料の削減や、 6 か月での移行完了（従来の方式なら 3 年から 5 年との見積もり）といった成果を掲げる。いずれも事業者の自己申告で、独立した検証は見つからなかった。
  • Software AG 側 : 2025 年の報道では、 Adabas & Natural は ARIS と並ぶ二つの中核事業として残された。

移行事例の費用や期間の数字は、事業者の宣伝に近い。一方で、「使用料が高い」「技術者が減っている」という動機は、複数の事業者が共通して挙げている。
