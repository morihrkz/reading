GitHub Pages に Cloudflare を重ねたら、証明書の更新が止まった
――Error 526 の原因と、 Cloudflare Pages への移行を読み解く

When a CDN Proxy Silently Blocks Certificate Renewal: A Walkthrough of a GitHub Pages Outage and Its Migration to Cloudflare Pages

ある朝、いつものように自分のサイトを開くと、見慣れない画面に「 526 」という数字が出ていた。コードは何も変えていない。サーバーを触った覚えもない。それでも、サイトは約 39 時間、誰にも見られない状態になっていた。 [1]

犯人は、 90 日ごとに自動で行われるはずだった「証明書の更新」だった。 GitHub Pages を使っていれば普段は目に入らないこの仕組みが、ある条件のもとで静かに止まる。本稿は、何が起き、なぜ止まり、どう直し、どう作り直したのかを、前提知識がなくても追えるように解説する。

【方法と限界】 本稿は、個人開発者が公開した復旧記録 [1] を読み解く解説である。原因の説明には、原典自身が「推定」と断っている部分が含まれる。そのため、確認できた事実（ API の応答、復旧後の状態など）と、そこから導かれる解釈は区別して書く。扱うのは一つの個人サイトの事例であり、 GitHub Pages 全般で必ず起きる現象として一般化はしない。公式ドキュメントへのリンクは原典が示したものを引用しており、本稿で改めて内容を突き合わせたわけではない。

1. 先に結論：何が壊れ、誰に関係するのか

最初に要点だけ置いておきます。細部が分からなくても、ここだけ持ち帰れば十分です。

  • 起きたこと
    GitHub Pages に自分のドメインを割り当て、さらに Cloudflare を間に挟んで公開していたサイトで、 HTTPS 用の証明書が更新されずに期限切れになった。サイトは Error 526 を返し続けた。
  • 原因（推定）
    Cloudflare を間に挟むと、 GitHub が証明書の更新時に行う「このドメインは本当に GitHub Pages を向いているか」の確認が通らなくなる。初回の発行はこの構成にする前だったので成功し、最初の更新で初めて失敗した。
  • 直し方
    応急処置は、 Cloudflare の経由を一時的にやめて証明書を取り直すこと。根本対策は、証明書の管理を Cloudflare に一本化するため、公開先を Cloudflare Pages へ移すことだった。

では、これは誰の話なのでしょうか。原典で問題になったのは「自分のドメイン」と「 Cloudflare のプロキシ」と「 GitHub Pages 」の組み合わせです。ユーザー名.github.io をそのまま使っている場合に同じことが起きるのかどうかは、原典からは分かりません。一方、この組み合わせに心当たりがある人にとっては、他人事ではありません。最後の節に、自分のサイトで確かめる手順をまとめました。

2. 前提知識：証明書と「 90 日」の正体

2.1 HTTPS の裏側にある証明書

アドレスバーの鍵マークは、通信が暗号化されていることを示します。暗号化の前提として、ブラウザは「いま話している相手は、本当にそのドメインの持ち主か」を確かめる必要があります。その身分証明にあたるのが「サーバー証明書」です。証明書には有効期限があり、切れた証明書をブラウザは信用しません。

2.2 90 日ごとの自動更新と ACME

GitHub Pages は、自分のドメインを割り当てたサイトの証明書を、認証局の Let's Encrypt から自動で取得し、自動で更新しています。 [2]Let's Encrypt の証明書の有効期限は 90 日です。短い期限をあえて採用し、更新を自動化することで安全性を保つ設計になっています。

この自動化に使われる約束事が ACME です。発行の前に、認証局は申請者に「そのドメインを実際に管理していること」を証明させます。この検証を「認可」と呼びます。 GitHub の場合、ドメインの DNS が GitHub Pages の IP アドレスを直接返しているかどうかを確認します。原典の説明に基づくと、この確認は初回の発行だけでなく、更新のたびに行われます。

ここまでの整理
証明書は 90 日で切れる。更新は自動だが、毎回「ドメインが GitHub Pages を直接向いているか」の確認を通す必要がある。この確認が通らなくなると、更新だけが静かに止まる。

3. 構成を整理する： Cloudflare を間に挟むと何が変わるのか

3.1 DNS と二つのドメインの形

DNS は、ドメイン名を IP アドレスに変換する電話帳のような仕組みです。サイトのドメインには、サブドメインを付けない形（ miraimirror.app 、以下「 apex 」）と、 www を付けた形の二つがあり、それぞれ別に設定します。原典のサイトでは、 apex は A レコード（名前を IP アドレスに直接結びつける設定）、 www は CNAME レコード（別の名前への「転送先の指定」）で GitHub Pages を向けていました。

3.2 オレンジ雲とグレー雲

Cloudflare の DNS 設定には、レコードごとに「プロキシ状態」のスイッチがあり、ダッシュボードでは雲のアイコンで表示されます。 [3]

  • オレンジ雲（プロキシ済み）
    名前を引くと Cloudflare の IP が返る。通信は Cloudflare のサーバー（エッジ）を経由して本来の公開先（オリジン）に届く。キャッシュや URL の書き換え、リダイレクトなど、 Cloudflare の機能が効く。
  • グレー雲（ DNS のみ）
    名前を引くとオリジンの IP がそのまま返る。ブラウザとオリジンが直接つながり、 Cloudflare の機能は効かない。

原典の筆者は、 apex をオレンジ雲にしていました。 URL の書き換え機能で /app のような拡張子のないきれいな URL （クリーン URL ）を実現するためです。 www はグレー雲のままでした。

3.3 証明書は二枚ある

ここが本稿でいちばん大事な図です。プロキシを挟むと、ブラウザが見る証明書と、 Cloudflare がオリジンに接続するときに確認する証明書は、別々の二枚になります。

どこまで厳しく確認するかは、 Cloudflare の「 SSL/TLS モード」で決まります。原典のサイトは最も厳格な Full (Strict) でした。このモードでは、オリジンの証明書が失効していると、 Cloudflare は接続そのものを拒否します。

項目原典のサイトの構成
公開先GitHub Pages （ private リポジトリ、 GitHub Actions で配信）
apexA レコード 4 本、オレンジ雲（クリーン URL のために 2026 年 7 月 24 日に有効化）
wwwGitHub への CNAME 、グレー雲
SSL/TLS モードFull (Strict)
大きなファイルCloudflare R2 （ファイル置き場）から配信

4. 障害の発生： Error 526

2026 年 10 月 11 日の 10 時過ぎ、サイトを開くと Cloudflare のエラー画面が出ました。画面には三つの箱が並び、「ブラウザ」と「 Cloudflare 」は正常 (Working) 、いちばん右の「 Host 」だけがエラーです。 Cloudflare までは届いているのに、その先のオリジンで止まっている、という意味です。

この「 526 」は、 Cloudflare が返すエラーの一つで、オリジンの証明書を検証できなかったことを示します。 Full (Strict) のモードで、証明書の失効、自己署名、ホスト名の不一致などがあると返されます。 [4]

証明書の期限は 2026 年 10 月 9 日 19:20 （日本時間）でした。 Full (Strict) は失効した証明書を即座に拒否するため、この時刻から 526 が出ていたと考えられます。 Cloudflare の分析画面でも、 5xx 系のエラーは 10 月 9 日の区間から出始めており、内訳は 526 が 354 件で、ほぼすべてを占めていました。

日時出来事
2026 年 7 月 11 日GitHub Pages の証明書を初回発行。まだプロキシ化前だったので成功
7 月 24 日apex をオレンジ雲に変更（クリーン URL 化）
10 月 9 日 19:20証明書が期限切れ。 526 が出始める
10 月 11 日 朝筆者がアクセスして初めて気づく
10 月 11 日 10:39暫定復旧。ダウンタイムはおよそ 39 時間

外形監視（外から定期的にサイトを見に行く仕組み）を入れていなかったため、気づけたのは筆者が自分でアクセスした時でした。ここに、後で触れる反省が集約されています。

5. 原因を突き止める

5.1 www 経由で、オリジンの様子を直接見る

プロキシが間にあると、オリジン本体の様子は見えません。そこで、グレー雲のままだった www を使います。こちらは GitHub Pages に直接つながるので、証明書の実物を見られます。まず、二つのアドレスにアクセスして応答を比べました。

curl -sS -o /dev/null -w "%{http_code}\n" https://miraimirror.app/
# 結果: 526 （ Cloudflare 経由）
curl -sS -o /dev/null -w "%{http_code}\n" https://www.miraimirror.app/
# 結果: curl: (60) SSL certificate problem: certificate has expired

後者のエラーは「証明書が期限切れ」と、はっきり言っています。次に、証明書の中身を取り出す openssl コマンドで有効期間を確認すると、 notAfter（失効日時）は 2026 年 10 月 9 日 10:20 (UTC) でした。初回発行の証明書が一度も更新されないまま、期限を迎えていたことになります。一方、 Cloudflare 側の証明書は 12 月 7 日まで有効で、問題はオリジン側だけでした。

5.2 決め手は GitHub の API が返す状態

では、なぜ更新されなかったのか。手がかりは、 GitHub の API にありました。 gh は GitHub 公式のコマンドラインツールで、 gh api で API の応答をそのまま見られます。 [5]

gh api repos/<owner>/<repo>/pages -q .https_certificate
# {
#   "state": "bad_authz",
#   "description": "The ACME authorization is in a bad state. We need to start over.",
#   "domains": ["miraimirror.app", "www.miraimirror.app"],
#   "expires_at": "2026-10-09"
# }

state が bad_authz でした。先ほどの ACME の「認可」が失敗した状態で止まっている、という意味です。設定画面よりも API のほうが、状態が具体的に出ます。

5.3 なぜ認可が失敗したのか

原典は、プロキシ化そのものが原因だと考えています。理由は三つの事実の連鎖です。

  1. オレンジ雲の apex は、 Cloudflare の IP アドレスに解決される。
  2. GitHub は更新時に、ドメインが GitHub Pages の IP を直接返しているかを DNS で確認する。プロキシ配下の apex は、この確認を通らない。
  3. 証明書は apex と www を一枚でまとめて扱っている。 www が GitHub を直接向いていても、 apex の確認が通らなければ、更新全体が失敗する。

これで時系列の謎も解けます。初回発行（ 7 月 11 日）はプロキシ化（ 7 月 24 日）より前だったので成功し、プロキシ化後の最初の更新で失敗した。つまり、クリーン URL 化の時点で「次の更新は失敗する」状態ができあがっていて、 90 日後に表面化したのです。

事実と推定の線引き
GitHub の内部で ACME のどの段階が失敗したのかは、外からは見えません。原典が確認できた事実は二点だけです。プロキシ中は state が bad_authz だったこと、グレー雲に戻して再設定したら数分で approved になったこと。「プロキシが原因」という説明は、この二点から導いた推定にとどまります。

もう一つ、見落とせない点があります。筆者は以前の記事に「 www の CNAME をグレー雲のままにしておけば、 GitHub 側の証明書の自動更新はこれまでどおり機能する」と書いていました。上の三点目のとおり、これは誤りでした。「まれに失敗する事例がある」と運用メモに書き添えていた現象が、そのまま起きたのです。

6. 暫定復旧：三つの手順

まずはサイトを戻すのが先です。原典は、前の記事に書いていた手順どおりに復旧しています。

  1. apex の A レコード 4 本をグレー雲に戻す
    プロキシ状態を「 DNS のみ」に変える。 www の CNAME はもともとグレー雲なので触らない。 R2 のカスタムドメインはプロキシが前提なのでそのままにする。
  2. Custom domain を再入力して、証明書を再発行させる
    リポジトリの Settings → Pages → Custom domain を一度削除し、同じドメインを入れ直して保存する。 GitHub 側の発行処理がやり直しになる。
  3. オレンジ雲に戻して、動作を確認する
    数分後、 gh api で state が approved になり、新しい証明書（期限は 2027 年 1 月 9 日）が出たのを確認してから、 A レコードをオレンジ雲に戻す。

気づいてから約 15 分で復旧しました。ただし、一つ落とし穴がありました。

再入力すると「 Enforce HTTPS 」が外れる
Custom domain を再入力すると、 HTTPS を強制する設定が外れます。上の API 出力で https_enforced が false になっているのがその印です。そのままだと、 http:// でのアクセスが HTTPS に転送されません。同じ画面で再度チェックを入れ、 http:// から https:// への 301 転送と、 www から apex への 301 転送が返ることを確認しています。

7. 再発防止：作業を自動化するか、構成を変えるか

復旧したとはいえ、構成は何も変わっていません。新しい証明書の期限も 90 日後で、このままでは同じ失敗が繰り返されます。 Let's Encrypt は失効の 30 日前までの更新を推奨しているため、実際には 60 日ごとの手作業になります。原典はここで二つの案を比べました。

案内容評価
更新作業を GitHub Actions で自動化グレー雲化 → Custom domain 再設定 → approved を待つ → Enforce HTTPS → オレンジ雲に戻す、を 60 日ごとに自動実行する可能。ただし発行の遅れや失敗時の再試行を設計する必要があり、根本原因（プロキシと ACME の衝突）は残る
Cloudflare Pages へ移行証明書の発行と更新を Cloudflare に一本化する採用。オレンジ雲を前提に作られているので、衝突が原理的に起きない

Cloudflare Pages は、 Cloudflare が提供する静的サイトのホスティングです。サイトのファイルを Cloudflare のエッジから直接配信し、カスタムドメインの証明書も Cloudflare が自動で発行、更新します。 [6]

決め手は三つありました。一つ目は、証明書の管理者が Cloudflare だけになり、根本原因が消えること。二つ目は、 URL の書き換えやリダイレクトのルール、 R2 、アクセス解析がどれもドメイン単位の設定なので、公開先が変わっても引き継げること。三つ目は、サイトを組み立てる工程はそのままで、アップロードの手順を差し替えるだけで済むことです。

見送った案もあります。「 www もオレンジ雲にして Cloudflare 側で転送する」は、 apex 側の失敗が残ります。「 apex をグレー雲に戻して GitHub 直配信にする」は、クリーン URL を失います。

8. 移行の実際：まずは並行稼働

移行の進め方で光るのは、順序です。本番のドメインを切り替えるまでは、本番を GitHub Pages のまま動かしました。 GitHub Pages の公開停止は最後に回し、問題が起きても DNS を戻せば切り戻せる状態を保っています。

8.1 認証情報の用意

GitHub Actions （ GitHub 上で自動処理を走らせる機能）から Cloudflare にデプロイするには、 wrangler という公式のコマンドラインツールを使い、アカウント ID と API トークン（アクセス用の合い鍵）で認証します。 [7] 原典のトークンは、デプロイ専用に新しく作り、権限は「 Cloudflare Pages の編集」の一行だけに絞っています。ゾーンや DNS の権限は不要で、既存の広い権限のトークンは流用していません。迷いやすい点として、アカウント ID は右上のメールアドレスではなく、 Workers & Pages 画面の「アカウントの詳細」などで確認します。

8.2 デプロイを wrangler に差し替える

GitHub Pages 向けの二つの公式ステップ(upload-pages-artifact と deploy-pages)を、 wrangler によるアップロードに置き換えます。サイトの組み立てなど既存の処理はそのままです。核心は次の一行です。

npx --yes wrangler@4 pages deploy _site --project-name "$CF_PAGES_PROJECT" --branch main

_site フォルダの中身を、 Cloudflare Pages のプロジェクトにアップロードします。あわせて、プロジェクトが存在しなければ作成するステップも置きました。 wrangler は作成するかどうかを対話形式で尋ねてきますが、自動実行の場では答えられないためです。

デプロイに成功すると、 *.pages.dev という確認用のアドレス（プレビュー URL ）でサイトが見られます。本番はまだ GitHub Pages のまま、ここで検証を進めます。

9. プレビューで見つかった三つの罠

並行稼働のおかげで、本番を切り替える前に三つの仕様差に気づけました。 GitHub Pages から Cloudflare Pages へ移る人が踏みやすい場所でもあります。

9.1 拡張子 .html が剥がされ、 308 で転送される

Cloudflare Pages は URL の .html を自動で取り除き、拡張子付きの URL へのアクセスを転送します（実測では 308 ）。この挙動は公式ドキュメントにも記載がありますが、無効にする設定はありません。 [8]

原典のサイトの本体は index.dc.html や app.dc.html という名前のファイルです。幸い /app.dc でも正常に描画されたため、ファイル名はそのままにしました。問題になったのは、クリーン URL のために作った URL 書き換えルールのほうです。書き換え先が .dc.html のままだと、 Cloudflare Pages が 308 を返し、アドレスバーが /index.dc に変わってしまいます。この修正は、本番の切り替え時に行いました。

9.2 404.html が無いと、存在しないパスが 200 を返す

存在しないパスにアクセスしても、トップページが 200 （正常）で返ってきました。 Cloudflare Pages は、ルートに 404.html が無いプロジェクトを SPA とみなし、知らないパスにトップページを返す仕様です。

用語メモ： SPA フォールバック
SPA (Single Page Application) は、 /users/123 のようなパスをブラウザ側のプログラムが処理するため、サーバーはどのパスにも同じ index.html を返す必要があります。この動作を SPA フォールバックと呼びます。

これは見た目だけの問題ではありませんでした。原典のアプリには「アニメーションの専用ファイルが 404 なら、既定のものを使う」という、 404 を前提にした分岐があります。 HTML が 200 で返ってくると、この分岐が働かず、動作不良につながります。対策は、自己完結した 404.html をリポジトリに追加し、公開フォルダのルートへコピーすることでした。

9.3 CORS を直しても、古い応答が残り続ける

三つ目は Cloudflare Pages ではなく、 R2 とキャッシュの話です。 CORS は、あるサイトのページが別のドメインのファイルを読み込んでよいか、ブラウザが確認する仕組みです。許可するサイトは、 R2 側に登録しておきます。 [9]

原典では、プレビュー URL を R2 の許可リストに追加した後も、ファイル一つだけ CORS エラーが続きました。調べると、リクエストの出どころを示す Origin ヘッダーの値ごとに、 Cloudflare のキャッシュが別々に保たれていることが分かりました。許可リストに追加する前に、「許可なし」の応答がキャッシュされており、設定を直した後もそれが返り続けていたのです。

厄介なことに、ダッシュボードの URL 指定のパージ（キャッシュ削除）では、この種のキャッシュは消えません。公式ドキュメントによると、 URL 指定のパージは Origin ヘッダーをキャッシュの識別に含むものを消さず、ダッシュボードからはヘッダーの値を指定できないためです。 [10] 原典は、同じ画面で「ホスト名」を選び、ホスト全体のキャッシュを消すことで解決しました。アセット配信専用のドメインなので、全消去しても、次のアクセスで取り直すだけで済みます。

切り分けのコツ
「 CORS の設定」と「すでにキャッシュされている応答」は別物です。設定を直したのに症状が変わらないときは、後者を疑います。なお、確認に curl -I を使うと、キャッシュを経由しない別の応答になるため、現象を再現できません。ブラウザと同じ GET で確かめる必要があります。

10. 本番ドメインの切り替え

10.1 apex を割り当てる

Cloudflare Pages のプロジェクトにカスタムドメインを追加すると、既存の A レコード 4 本を CNAME に置き換える変更が提示され、「ドメインをアクティブにする」を押すだけで終わりました。 DNS の規則上、 apex には CNAME を置けませんが、 Cloudflare は CNAME を内部で IP アドレスに解決して返す「 CNAME フラット化」でこの制約を回避しています。 [11]

あわせて、 URL 書き換えとリダイレクトのルール計五本を、 Cloudflare Pages の仕様に合わせて修正しました。書き換え先を .dc.html から .dc に変え、 .dc 付きのパスへの直接アクセスも 301 で正規の URL に寄せています。

10.2 www は「転送専用」にする

www の役割は、 apex へ転送するだけです。コンテンツを配信する必要はないため、 Cloudflare Pages のカスタムドメインには追加せず、転送専用のホスト名にしました。公式の手順も同じ考え方です。 [12]DNS では、 www の CNAME を、ダミーのアドレスを向く AAAA レコード（ 100:: 、オレンジ雲）に置き換えます。

用語メモ： AAAA 100::
IPv6 で「破棄用」として予約されたアドレスです。オレンジ雲にしておけば、リクエストは Cloudflare のエッジで受け止められ、リダイレクトルールで転送されるため、このアドレスに実際に接続されることはありません。オリジンを持たない転送専用ホスト名で、よく使われる書き方です。

10.3 切り替え後に全 URL を確認する

ルール修正後、 curl で全 URL のステータスコードをまとめて確認しました。ダッシュボードの見た目ではなく、実際の応答で確かめる点が肝心です。

11. 外形監視と後片付け

11.1 次は、自分で気づけるように

39 時間も気づけなかった反省から、 GitHub Actions で外形監視を追加しています。毎朝一回と、デプロイの直後に、 13 項目を確認する仕組みです。確認するのはステータスコードだけではありません。ページ本文の目印、リダイレクト、未知のパスの 404 、 CORS 、三つのホスト名の証明書の残り日数（ 14 日以上）まで見ます。異常があれば Issue を自動で起票し、復旧すれば自動で閉じます。

本文の目印まで見るのは、先ほどの 404.html の例のように、何でも 200 を返してしまう状況ではステータスコードだけでは異常を検知できないからです。頻度が一日一回なのは、 GitHub Actions の実行時間が一分単位で切り上げて計上され、頻繁に走らせると無料枠を圧迫するためでした。

11.2 後片付けで、あえて残したもの

最後に GitHub Pages の公開を停止し、開発用ドキュメントを書き換えて移行は完了です。ただし、ドメイン所有の確認用に作った TXT レコードは、あえて残しました。 GitHub の「 Verified domain 」の設定を維持すると、第三者が自分のドメインを勝手に GitHub Pages で使うことを防げるためです。配信に使わなくなっても、乗っ取り対策として価値があります。 [13]

移行後も残る注意点は、原典が運用メモに書いています。 JS や CSS はブラウザに最大 4 時間残るため、キャッシュ対策の仕組みは引き続き必要なこと。 *.pages.dev のプレビュー URL が公開状態で存在していて、検索エンジンよけやアクセス制限を検討する余地があること。 GitHub Pages に切り戻すには、公開の再開と DNS の復元の両方が必要なことです。

12. あなたのサイトで確かめること

ここまでの内容を、手を動かせる形に直します。原典の「学び」に沿って整理しました。

  1. プロキシを挟んでいるか調べる
    Cloudflare などを経由して GitHub Pages を公開しているなら、今回と同じ構成です。 DNS の設定で、 GitHub Pages を向いているレコードがオレンジ雲になっていないか見る。
  2. 証明書の状態と期限を見る
    gh api repos/<owner>/<repo>/pages -q .https_certificate を実行し、 state が approved か、 expires_at がいつかを確認する。 bad_authz が見えれば、原因はほぼ確定する。
  3. 「たまに失敗する」を対策タスクにする
    原典の筆者が最大の反省とした点。運用メモに書いて満足せず、 Issue にして期限を管理していれば、 39 時間の障害は防げた。
  4. 外形監視を入れる
    証明書の残り日数まで見ておけば、失効前に気づける。
  5. 証明書の管理者を一つにまとめる
    CDN とオリジンで別々に証明書を持つと、片方の失効が全体の障害になる。
  6. 設定変更のたびに curl で全 URL を確認する
    ダッシュボードの見た目より、実際のステータスコードが確かな根拠になる。

13. おわりに

この事例の怖さは、壊れたタイミングと原因のタイミングが 70 日以上ずれていたことにあります。クリーン URL を実現するための設定変更が、証明書の更新という別の仕組みを、静かに止める仕込みになっていました。便利さのために一つ設定を足したとき、その設定が別の仕組みの前提を壊していないか。その問いは、 GitHub Pages に限らず、ほかの構成にも通じます。

原典の筆者は、障害のおかげで構成はむしろ単純になったと振り返っています。 GitHub Pages の前段に Cloudflare を挟んでいる人は、まず証明書の状態と期限を一度だけ確かめてみてください。
